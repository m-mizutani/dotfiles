# 図を中心にした報告資料の作成スキル

「報告せよ」「レポートせよ」と指示されたときに、報告する内容を整理し、図を中心に構成した Artifact として公開する。

この資料の目的は、**対象について予備知識がない読み手が、資料を上から読むだけで、対象の全体像と結論を理解できること**である。読み手が用語を調べたり、本文の項目どうしの関係を頭の中で組み立て直したりする必要があるなら、その資料は目的を果たしていない。

報告を求める人は、資料を自分で読むだけでなく、対象を知らない別の人に見せることが多い。そのため、この会話の経緯を知っていることを前提にしない。

## 役割が近いスキルとの違い

| スキル | 対象 | 出力 |
|-------|-----|-----|
| このスキル | 調査結果、作業結果、障害、現状、仕組みの説明など、報告を求められた事項全般 | 対象を理解するための報告資料 |
| `build-review-report` | 完了したコード変更 | 変更内容とテストによる検証状況 |
| `decision-brief` | ユーザーが選ぶ必要がある事項 | 選択肢の比較と回答欄 |
| `design-doc-review-guide` | デザインドキュメントの PR | レビュアー向けの解説 |

報告の主題が上の3スキルのいずれかに該当する場合は、そちらを使う。報告の中にユーザーの判断が必要な事項が含まれる場合は、この資料では「判断が必要な事項」として1行で示すだけにし、判断材料は `decision-brief` で作る。

## 読み手の理解を最優先にする理由

文章と箇条書きを並べた報告は、書き手が知っている情報を並べただけで、読み手の理解を作らない。予備知識がない読み手は、次の3つを自分で行う必要があり、そこで読むのをやめる。

- 未定義の用語や識別子の意味を推測する
- 別々の段落に書かれた項目どうしの関係（どれがどれを呼ぶか、どれが先に起きるか、どれが原因か）を組み立てる
- 細部のどれが重要で、どれが補足かを判断する

このスキルでは、この3つの作業を資料を作る側が行う。用語は最初に使う箇所で定義する。関係は図で示す。重要度は、次の節で定める情報の区別と、構成の順序と分量で示す。

## 必ず伝える情報と補足の情報の区別

資料に書く情報を、次の2種類に分ける。

| 区別 | 判定基準 | 例 |
|-----|---------|---|
| **必ず伝える情報** | 読み手がこれを読まないと、結論、現在の状態、求められている行動のいずれかを誤解する、または説明できない | 結論、全体像の図、結論の理解に必要な概念、原因、影響範囲、残っている課題、確認できていない重要な前提 |
| **補足の情報** | 読まなくても結論は理解できるが、読み手が疑問を持ったときに確かめるために使う | 詳しい手順、ログの抜粋、計測の詳細な条件、検討して採らなかった案、関連するが主題ではない事実、根拠の一覧 |

判定に迷った情報は、「これを削除したら、読み手は結論を誤解するか」で判定する。誤解しないなら補足の情報である。

区別した情報は、読み手が画面上で見分けられるように配置する。補足の情報を本文と同じ見た目で並べると、読み手はすべてを読むか、読み飛ばしてよい箇所を自分で判断するかのどちらかになる。

- **補足の情報は折りたたむ。** `<details class="more">` に入れ、`<summary>` には中身が分かる名詞句を書く（「詳細」ではなく「タイムアウト値を決めた計測の条件」）。読み手は、気になった点だけを開いて確認できる
- **表示の濃淡を付ける。** 必ず伝える情報は通常の文字色と大きさで書く。本文中の短い補足は `.aside`（薄い文字色、小さい文字）にする。強調（`<strong>`）は、各節で読み手が最初に読むべき1文だけに使う
- **区画を分ける。** 結論は囲みに入れて資料の先頭に置く。各節は「図 → 図から読み取れる結論 → 折りたたんだ補足」の順にし、必ず伝える情報が節の上部に来るようにする。根拠の一覧のように資料全体の補足となる節は、節全体を折りたたむ
- **必ず伝える情報を折りたたまない。** 折りたたんだ中にしか書かれていない情報は、多くの読み手に読まれない。結論の理解に必要な図、課題、確認できていない重要な前提は、折りたたまずに表示する
- **補足の情報の量で資料を長く見せない。** 折りたたんでも、主題に関係しない情報は書かない

## 進め方

### Step 1: 報告の主題と読み手を決める

次の3点を1文ずつ書けるまで、資料を作り始めない。

1. **報告の主題** — 何について報告するのか。例: 「Webhook の配信が10月22日に3時間止まった原因と、現在の対処状況」
2. **読み手が資料を読んだ後に分かること** — 例: 「何が止まり、なぜ止まり、今は何が直っていて、何が残っているか」
3. **読み手に求める行動** — 承認、判断、作業、または「なし（情報共有）」

主題は会話の文脈から決める。直前まで行っていた調査や作業について「報告せよ」と言われた場合は、その調査や作業が主題である。主題の候補が複数あり、どれを選ぶかで資料の内容が大きく変わる場合だけ、`AskUserQuestion` で確認する。

想定する読み手は、**計算機科学とソフトウェア工学の一般的な知識はあるが、この対象の仕組み、用語、経緯を知らない人**とする。ユーザーが読み手を指定した場合（例: 「非エンジニアの上司向けに」）は、その読み手の知識に合わせる。

### Step 2: 事実を集めて確認する

報告に書く事実は、会話中に得た根拠を再利用し、足りないものだけを追加で確認する。

- 主張ごとに根拠（ファイルと行、コマンドの出力、ログ、ドキュメント、URL）を特定する
- **確認済みの事実**、**推測**、**未確認の事項**を区別して記録する。推測を事実として書かない
- 数値（件数、時間、割合）は、範囲と数え方を決めて1回数え、その数を使う
- 同じ対象を指す名前を1つに決める。会話中に複数の呼び方が使われていた場合は、リポジトリで定義された名前に統一する

調べる範囲が数十ファイルに及ぶ場合だけ、Agent（Explore）に範囲を区切って要約させる。数回のツール呼び出しで済む確認は自分で行う。

### Step 3: 読み手が理解に必要な概念を選ぶ

結論を理解するために読み手が知っている必要がある概念を、**3〜7個**選ぶ。概念とは、データの単位、構成要素、処理、状態、関係者などである。

各概念について次を確認する。

- それは何を表すか。1件が何に対応するか
- 他の概念とどう関係するか（呼び出す、保存する、含む、遷移する、原因になる）
- 読み手が知らない名前（リポジトリ固有の識別子、社内の略語）なら、どう言い換えるか

8個以上必要に見える場合は、粒度が細かすぎる。上位の単位（サービス、レイヤー、工程）に集約し、詳細は後の節で扱う。

### Step 4: 図の計画を立てる

**本文を書く前に、図の一覧を決める。** 本文は図を読むための説明として書く。先に本文を書くと、図が本文の項目を箱に置き換えただけのものになる。

各図について、**その図を見た読み手が答えられる問い**を1つ決める。問いが決まらない図は描かない。

| 読み手の問い | 図の種類 |
|------------|---------|
| 全体はどういう構成か。報告の対象はその中のどこか | 構成図（箱と矢印）。報告の対象を強調する |
| 処理はどの順序で進むか。誰が誰に何を渡すか | シーケンス図、または処理の流れ図 |
| 対象はどの状態をとり、何で次の状態に移るか | 状態遷移図 |
| いつ何が起きたか | タイムライン |
| 何が原因で何が起きたか | 因果の連鎖（原因→結果の矢印） |
| 変更前と変更後で何が違うか | 同じ配置の2枚の図を並べ、変わった部分を強調する |
| 量はどれだけか。どこに偏っているか | 棒グラフ、積み上げ横棒（`dataviz` skill を読む） |
| どれが完了し、どれが残っているか | 状態を色で示した一覧図、または構成図に状態を重ねた図 |

図の枚数の目安:

- 資料全体で**3枚以上**を基本とする。冒頭の全体像の図は必ず置く
- 各節に、その節の主張を示す図を1枚置く。関係や変化を含まない節（数値1つの報告など）だけ図を省いてよい
- 1枚の図に主張を2つ以上入れない。2つの主張が必要なら2枚に分ける
- ただし、**対応付けが必要な情報は1枚に重ねる**。「構成図」と「各構成要素の状態一覧」を別々に出すと、読み手が2枚を見比べることになる。構成図の上に状態を色で重ねる

図の描き方は `references/diagrams.md` を読む。あわせて `artifact-diagramming` skill を読み込む。

### Step 5: 資料の構成を決める

読み手が上から読み、必要な情報を得た時点で読むのをやめられる順序にする。

| 順序 | 内容 | 形式 | 表示 |
|-----|-----|-----|-----|
| 1 | **結論**: 報告の主題に対する答えを3〜5行。読み手に求める行動があればここに書く | 強調した囲み | 常に表示 |
| 2 | **全体像**: 対象の役割と構成。報告の対象が全体のどこにあるか | 図 + 2〜4行の説明 | 常に表示 |
| 3 | **重要な概念**: Step 3 で選んだ概念の意味と関係 | 図 + 用語の定義 | 常に表示 |
| 4 | **本題**: 何が起きたか / 何をしたか / どうなっているか。主題に応じて節を分ける | 節ごとに図 + 説明 | 図と結論は表示し、詳細は折りたたむ |
| 5 | **現在の状態と残っている課題**: 完了したこと、残っていること、次に行うこと | 状態を示した図または表 | 常に表示 |
| 6 | **確認できていない事項**: 推測で書いた箇所、未確認の前提 | 箇条書き | 結論に影響する事項は表示し、それ以外は折りたたむ |
| 7 | **根拠**: 参照したファイル、ログ、コマンド、URL | 表 | 節全体を折りたたむ |

Step 2 で集めた事実を、この時点で「必ず伝える情報」と「補足の情報」に分け、どの節のどの位置に置くかを決める。

順序 4 の節の分け方は主題から決める。例:

- 障害の報告: 発生した事象 → 原因 → 影響範囲 → 対処
- 調査の報告: 調べた問い → 分かったこと → 分かっていないこと
- 作業の報告: 目的 → 変更前の状態 → 行った変更 → 変更後の状態
- 仕組みの説明: 入力 → 処理の流れ → 出力 → 例外的な経路

テンプレートの節をそのまま埋めることを目的にしない。報告の主題に関係しない節は省く。

### Step 6: 本文を書く

本文は次の水準で書く。

- **用語は最初に使う箇所で定義する。** 定義は「何を表すか」と「1件が何に対応するか」を1文で書く。資料の末尾に用語集を置くだけで済ませない
- **1つの具体例を資料全体で使う。** 例えば「ユーザー A が注文を確定した場合」を全体像の図、処理の流れの図、障害の説明で共通に使う。節ごとに別の例を使うと、読み手はそのたびに状況を理解し直す
- **図の直前に、その図で何を見るかを1文で書く。** 図の直後に、図から読み取れる結論を1〜2文で書く
- **図と本文で同じ名前を使う。** 図のラベルが `OrderService`、本文が「注文処理」では、読み手は同じものか判断できない。両方を併記するなら初出で対応を示す
- **経緯を時系列で並べない。** 読み手が知りたいのは結論と現在の状態である。経緯は、結論の理解に必要な場合だけ書く
- **抽象的な評価語で済ませない。** 「重い」「不安定」「改善した」ではなく、計測値、件数、観測した動作を書く
- 確認済みの事実と推測を、文末の表現と表示（推測には「推測」のラベル）で区別する
- **Step 5 で補足の情報と判定したものは、`<details class="more">` または `.aside` に書く。** テンプレートに両方の使用例がある

日本語の書き方は `CLAUDE.md` の Japanese Replies に従う。

### Step 7: 予備知識がない読み手として読み直す

公開する前に、対象を知らない読み手として資料を上から読み、次のいずれかに当てはまれば直す。

- 定義していない識別子、略語、社内用語がある
- 冒頭の結論だけを読んでも、報告の主題に対する答えが分からない
- 図に凡例がない、または図の色・線・形の意味を本文から探す必要がある
- 図が本文の項目を箱に置き換えただけで、関係や変化を示していない
- 図と本文で同じ対象の名前が異なる
- 同じ具体例で、全体像から本題まで追えない
- 確認済みの事実と推測の区別が付かない
- 図を除くと読み手が理解できなくなる箇所がない（図が装飾になっている）
- 折りたたんだ部分をすべて閉じたまま読むと、結論、現在の状態、求められている行動のいずれかが分からない（必ず伝える情報を折りたたんでいる）
- 折りたたまれていない本文に、読まなくても結論を誤解しない情報が続いている（補足の情報を本文と同じ見た目で並べている）
- `<summary>` の文言から、開く前に中身が分からない

文章を足して直すのではなく、概念の選び方、図、説明の順序を直す。

### Step 8: 公開して報告する

1. `Artifact` ツールの `action: "quickstart"` を `intent: "other"` で呼び、その結果のページ設計の指示に従う。quickstart の結果がページ設計の指示を含まない場合は `artifact-design` skill を読み込む
2. `assets/report-template.html` をスクラッチパッドディレクトリにコピーし、`report-{主題を表す英小文字の slug}.html` という名前にする。スクラッチパッドディレクトリがない環境では、リポジトリルートの `tmp/` に置く
3. テンプレートの `{{...}}` をすべて置き換え、不要な節を削除する。プレースホルダーを残したまま公開しない
4. `Artifact` ツールでそのファイルを公開する。初回の公開では `icon` に `report` を、`description` に報告の主題を1文で渡す
5. 修正する場合は、同じ `file_path` で再公開して同じ URL を保つ

ターミナルの返答には次を書く。資料の URL だけを示して終えない。

- 結論（資料の冒頭と同じ内容を3〜5行）
- 読み手に求める行動。ない場合は書かない
- 確認できていない事項があれば、その件数と主なもの
- 資料の URL

資料のファイルは `git add` しない。作業用の成果物である。

## 書かないこと

- **調査や作業の経緯の時系列の記録。** 結論の理解に必要な部分だけを書く
- **図と表で同じ情報を2回示すこと。** 関係と構造は図、個別の項目と根拠の場所は表に書く
- **凡例のない図、問いのない図。** 読み手の理解を助けない図は、読む量を増やすだけである
- **mermaid と ASCII Art。** 状態を色で重ねる、対象を強調する、ライトテーマとダークテーマの両方で読めるようにする、という要件を満たすため、inline SVG または HTML と CSS で描く
- **推測を事実として書くこと。** 確認できなかった事項は「確認できていない事項」に書く
- **すべてを同じ見た目で並べること。** 必ず伝える情報と補足の情報の区別を、折りたたみ、表示の濃淡、区画で示す
- **会話中に作った呼び名。** 会話の中で一時的に使った呼び名は、読み手にとって未定義の語である。リポジトリで定義された名前か、動作の説明に置き換える
