# 判断依頼資料の作成スキル

ユーザーに決めてもらう事項を1つの資料にまとめ、そのページ上で回答してもらうスキル。

この資料の目的は、読み手が調査の経緯を読まずに、次の3点を理解し、その場で決められるようにすることである。

- 何を決めるのか
- 各案で何が変わり、どの点が異なるのか
- 決めた後に何が起きるのか

読み手が「何を決めればよいのか」「2つの案はどこが違うのか」を自分で考え直す必要があるなら、その資料は目的を果たしていない。

役割が近いスキルとの違い:

| スキル | 入力 | 出力 |
|-------|-----|-----|
| `brainstorm` | 実現方法がまだ決まっていないアイデア | 実現方法の調査結果。選択肢はこの段階で作られる |
| このスキル | **選択肢が出そろい、どれを採るかを決める段階の事項** | 選択肢の比較と、ユーザーの回答 |
| `build-review-report` | 完了した変更 | 変更全体と検証状況の一覧 |

## この資料でよく起きる誤り

次の4つは、いずれも読み手に追加の作業を求めるため、誤りとして扱う。

- **調査の経緯を時系列で並べる。** 読み手が知りたいのは、どの点で案が分かれるかである。経緯は、判断に影響する場合にだけ書く
- **各案を独立した段落で説明する。** 案Aの段落と案Bの段落を別々に読ませると、読み手が2つの段落を比べて違いを見つけなければならない。このスキルで最も起きやすい誤りである
- **比較項目を決めずに長所と短所を並べる。** 案ごとに別の観点で長所と短所を書くと、並べても比較できない
- **読み手がこの開発の実装を知っている前提で書く。** 選択肢の説明が識別子とファイル名だけで進むと、読み手は対象が何をするものかを推測しなければならない

## 原則1: すべての案を同じ比較項目で説明する

**比較項目を先に決め、すべての案を同じ比較項目について説明する。** 案ごとの詳しい説明は、比較項目ごとの違いを示した後に書く。

すべての案が同じ比較項目で説明されていれば、読み手は表を読むだけで違いが分かる。そうでなければ、読み手が各案の説明から比較項目を探し出す必要がある。その作業は資料を作る側が行う。

比較項目の条件:

- **選んだ案によって結果が変わる項目だけを比較項目にする。** どの案でも同じ結果になる項目は書かない。判断に役立たず、資料が長くなるだけである
- **通常は3〜5項目に絞る。** 小さな判断では、結果が異なる項目だけにする。数を合わせるために比較項目を作らない
- **何がどう変わるのかを具体的に書く。** 「保守性」「拡張性」のような語だけでは、読み手はどちらの案が優れているのかを判断できない。「新しい通知先を追加するときに変更が必要なファイル数」のように、観測できる値で書く

## 原則2: 読者のメンタルモデルの形成を最優先にする

**想定する読み手は、計算機科学とソフトウェア工学の知識はあるが、この開発の全体も実装の詳細も知らない人である。** その読み手が冒頭の説明だけで課題を理解でき、その後の比較表と選択肢を、用語を調べずに読める状態にする。

**最優先課題は、読者が判断に必要なメンタルモデルを形成することである。** 重要な概念の意味と関係、現在の動作（as-is）、目指す動作（to-be）、各案で変わる部分を説明できる状態にする。文字や項目を並べただけでは説明したことにならない。比較表や選択肢は、この理解を形成してから示す。

本文やテンプレートの項目を埋める前に、関連する実装と要求を読み、次を検討する。

1. **理解に必要な概念を選ぶ。** 読者は何を理解すれば各案の違いを判断できるか。データの単位、処理、状態、責務のうち、この判断を左右するものを特定する。各概念が何を表し、1件が何に対応し、他とどう関係するかを確かめる。識別子や構成要素の一覧で代用しない。
2. **現在と目標を同じ具体例で確かめる。** 誰が何をしたとき、現在は何が起き、変更後は何ができるようになるのか。入力、対象、処理、結果を揃えて説明する。共通の目標と、各案で異なる実現方法を区別し、未採用の案を決定済みの構造として描かない。
3. **原則として図で関係と変化を説明する。** データ構造、処理順序、状態遷移、責務、保存と参照など、理解に必要な関係を描く。図ごとに読者が答えられる問いを決める。現在と目標を同じ名称・単位・対応する配置で示し、維持する部分と変える部分を明示する。複数の図が必要なら使い、1枚にすべてを詰め込まない。関係や動作の変化がなく、値だけの比較を表で十分に示せる場合に限り図を省いてよい。
4. **読者が理解できる順序を選ぶ。** 冒頭は、対象の役割と今回実現したい結果を短く示す。その後に重要な概念と図、現在と目標の違いを説明し、その理解に基づいて決める事項を示す。未説明の識別子、保存先の列挙、変更ファイル、作業上の都合から始めない。小見出しは案件の内容から決め、確認項目をそのまま固定の節にしない。
5. **制約を関係する箇所で説明する。** 制約は、どのデータ、処理、関係、または案の結果を制限するかと一緒に説明する。冒頭に制約の一覧を置いても理解の代わりにはならない。「単純な解決方法がない理由」は冒頭の必須項目にせず、判断に影響する場合だけ各案の比較や補足に置く。

固有の用語は最初に使う箇所で意味を説明する。用語集を後から置くだけで済ませない。図と本文の対応は Step 6 に従う。

## 使う場合と使わない場合

| 状況 | 対応 |
|-----|-----|
| ユーザーが決める必要のある選択。小さく、容易に変更できる選択も含む | このスキルを使う。資料の長さは判断に必要な内容に合わせる |
| 選択肢が複数あり、後から変更する費用が大きい（アーキテクチャ、データモデル、外部契約、セキュリティ、永続化スキーマ） | このスキルを使う |
| 判断に必要な情報が多く、選択肢の比較に表や図が必要 | このスキルを使う |
| 手元の根拠ですでに結論が決まる | 自分で決めて進め、その理由を1行で報告する。比較のためだけに選択肢を並べない |
| ユーザーがすでに方向を示している | その方向で進める。選ばれなかった案を再び提示しない |
| 次の4点をまだ1文ずつ書けない: 何が問題か / 具体的な変更 / 外から観測できる動作の変更前と変更後 / 主な欠点 | 調査を続ける。4点を書けない案は提案ではない |

**判断1件につき資料は1つ**にする。同じ判断について資料や承認を繰り返し求めない。自分で決められる実装上の細かな選択は、このスキルを起動せず自分で決める。

## 進め方

### Step 1: 決めることを1文で書く

「何をどう決めるのか」を1文で書けるまで、資料を作り始めない。書けないなら、何を決めるのかがまだ特定できていない。

- 良い例: 「セッション情報の保存先を PostgreSQL のテーブルにするか、Redis にするか」
- 悪い例: 「セッション管理の設計方針」（何を選ぶのかが書かれていない）

未決の事項が複数ある場合は、事項どうしの依存関係を確認し、**最初に決める必要がある1件**を資料の主題にする。その後に決める事項は、資料の末尾に「この判断の後に決めること」として列挙するだけにする。複数の判断を1つの資料に入れると、回答がどの判断に対するものかが分からなくなる。

あわせて、**この判断が決まらないと、どの作業を進められないのか**を特定する。進められない作業がないなら、今ユーザーに尋ねる必要はない。

### Step 2: 各案の根拠を実際のコードで確認する

各案の説明は、実際のコード、spec、依存ライブラリのドキュメントで確認してから書く。記憶や一般論で書いた案は、ユーザーがその案を選んだ後に実装できないことが分かる場合がある。

少なくとも、各案について次を確認する。

- その変更が編集するファイルと、影響を受ける呼び出し元（`file:line` で示す）
- 同じ種類の処理がリポジトリ内にすでにあるか。ある場合、それが意図して統一された書き方か
- そのリポジトリの `CLAUDE.md` と `.claude/rules/` に、この判断を制約する規定があるか
- 外部のツールやライブラリの設定に関わる場合は、**使用中のバージョンの公式ドキュメント**に書かれた動作

確認できなかった点は削除せず、資料の「確認できていない前提」に書く。

### Step 3: 重要な概念と現在・目標の動作を図で説明する

原則2に従い、Step 2 で確認した実装から重要な概念と関係を選び、図と同じ具体例で現在と目標の動作を説明する。資料を作る側が判断事項を先に特定することと、読者に保存先の選択肢を最初に読ませることを混同しない。

書き終えたら、**この開発を知らない読者として読み直す**。次のいずれかに当てはまる場合は書き直す。

- 意味を説明していないリポジトリ固有の識別子や略語がある
- 図と本文から、重要な概念の違い、1件の単位、相互の関係を説明できない
- 同じ具体例の入力から処理と結果まで、現在と目標の動作を追えない
- 共通の目標と、各案で異なる実現方法を区別できない
- 制約がどのデータ、処理、関係に作用し、各案の結果にどう影響するか分からない
- 図が文章の項目を箱に置き換えただけで、関係や変化を説明していない

該当する場合は、文章を足すだけで済ませず、概念の選び方、図、説明順を直す。提示前にも同じ確認を行い、読者が各案で変わる部分を説明できるか、実際に本文と図から読み取る。

### Step 4: 比較項目を決める

各案の説明を書く前に、原則1の条件を満たす比較項目を決める。通常は3〜5項目とし、小さな判断では必要な項目だけにする。

比較項目を決めた結果、**どの比較項目でも他の案と結果が変わらない案**があれば、その案は選択肢から除く。

### Step 5: 2つの基準それぞれで推奨する案を選ぶ

推奨は1つにまとめず、**異なる2つの基準で選んだ案を並べて書く**。どちらも最終的な結論ではなく、基準を明示した判断材料である。最終的にどの案を採るかはユーザーが決める。

| 基準 | 選び方 |
|-----|-------|
| 長期の保守性を優先する基準 | 長期的な保守性、データモデルの一貫性、抽象化の適切さで選ぶ。**既存の実装を前提にしない。** 実装量と互換性を壊す変更の有無は、選ぶ理由にしない |
| 実装コストも考慮する基準 | 実装コスト、互換性を壊す変更を避けること、上記の保守性の3つを比べて選ぶ |

それぞれの基準について、**その基準でその案を選んだ理由**と、**その案を採用した場合に受け入れる欠点**を書く。

- **2つの基準で同じ案を選んだ場合は、そのまま同じ案を書く。** 違いを作るために片方を別の案に変えない。2つの基準で結果が一致したこと自体が、読み手にとって判断の根拠になる
- **2つの基準で別の案を選んだ場合は、実装コストも考慮した案を採ったときに残る問題と、後から保守性を優先した案へ移行するために必要な作業を書く。** 読み手にとって、この情報が最も必要である
- **実装コストを理由に、保守性を優先する基準の案を変えない。** 変えると、2つの基準で同じ観点から選んだことになり、2つを並べる意味がなくなる

「ある比較項目を優先するならこの案」という条件付きの推奨は、2つの基準の推奨で説明が足りる場合は書かない。どちらの基準でも選ばれなかった案が、特定の比較項目を優先する場合にだけ最適になるときに限り、書き加える。

### Step 6: 資料を作成して公開する

1. `artifact-design` skill を読み込む（Artifact の設計指針。省略しない）
2. `assets/decision-template.html` を作業ディレクトリにコピーする
   - spec がある場合: `.spec/{slug}/decision-{主題}.html`（slug はブランチ名の slash 以降）
   - spec がない場合: `tmp/decision-{主題}.html`（リポジトリルート直下の `tmp`）
3. テンプレート内の `BRIEF` JSON を書き換える。**編集するのは JSON だけ**で、スタイルと描画スクリプトは変更しない。ページはこの JSON から描画され、ユーザーの回答もこの JSON に書き込まれる
4. `Artifact` ツールで公開する。`capabilities` には必ず `{"artifact": {}}` を渡す（ページ上で回答を記録するために必要な宣言）。初回の公開では `icon` に `decision` を渡す
5. ターミナルの返答にも、判断に必要な内容を書く。資料の URL を示しただけで判断を求めない。返答には次を書く
   - 対象の役割と実現したい結果、重要な概念、現在と目標の動作
   - その理解に基づいて決めること（1文）
   - 各案について、何を変更するか（追加・変更するテーブル、カラム、関数、設定など、変更対象ごとの内容を含む）と、外から観測できる動作の変更前と変更後
   - 2つの基準それぞれで推奨する案と、その理由
   - 資料の URL

JSON の各フィールドの意味と、回答がどのように届くかは `references/answering.md` を読む。

図は2か所に入れられる。前者で判断の前提を理解できるようにし、後者は案ごとの違いを示す必要がある場合に使う。各フィールドには複数の SVG を配置してよい。

| 配置する場所 | JSON フィールド | 図に描く内容 |
|---------|---------------|--------|
| 判断事項より前 | `problem.figureSvg` | 重要な概念の関係、現在と目標の動作。制約は作用する箇所に示す |
| 比較表の直後 | `figureSvg` | 案によって構造がどう変わるか |

2つの図に共通する制約:

- **原則として図を使う。** 原則2の省略条件に当てはまる場合だけ省く。図の直前に何を見るかを説明し、直後に重要な条件と判断事項との関係を書く。`figureIntro` と `figureCaption` はこのために使う
- 箱が概念、データ1件、処理、実行1回のどれか、矢印が参照、呼び出し、データの移動、状態遷移のどれかをラベルや凡例で示す。理解に必要な多重度、順序、所有関係、同期・非同期を省かない
- 現在と目標、各案で同じ概念の名称・単位・対応する配置を揃え、変わる部分を明示する。必要なら複数の図を使い、読み手に対応関係を推測させない。本文・図・具体例の用語と値を一致させ、確認済みの動作と提案を区別する
- inline SVG または HTML と CSS で描く。mermaid と ASCII Art は使わない
- 凡例を必ず付ける。ライトテーマとダークテーマの両方で読めるようにする（色のトークンはテンプレートに定義済み）

### Step 7: 回答を受け取って作業を続ける

ユーザーがページ上で案を選ぶと、ページが自身の新しいバージョンを公開する。資料を公開した時点で、このセッションは資料の更新を監視しているので、再公開の通知が届く。

1. 通知を受けたら、`Artifact` ツールの `action: "read"` でその URL を読み、`BRIEF` JSON の `decision` を確認する
2. 選ばれた案と、ユーザーが書いたメモを1行で確認として述べ、その案で作業を始める
3. ユーザーがターミナルで直接答えた場合は、それを回答として扱う。ページ上での選択を待たない

ページが再公開されると、ローカルのファイルの内容は公開中の内容より古くなる。**資料を再び公開する場合は、ローカルのファイルから公開せず、先に `action: "read"` で公開中の内容を読んでから編集する。**

## 資料の構成

読み手が上から読み、判断に必要な情報を得た時点で読むのをやめられる順序で並べる。

| 順序 | 内容 |
|-----|-----|
| 1 | 対象の役割と実現したい結果、重要な概念の関係を示す図、同じ具体例による現在と目標の動作。制約は関係する箇所で説明する |
| 2 | その理解に基づいて決めること（1文）、決まらないと進められない作業、判断時期に影響する期限 |
| 3 | 比較項目ごとに各案の結果を示す表。案の実現方法を理解するために必要な図を添える |
| 4 | 2つの基準（長期の保守性を優先する基準 / 実装コストも考慮する基準）で推奨する案と、2つが異なる場合に残る問題 |
| 5 | 回答欄（各案を選ぶ操作とメモ欄） |
| 6 | 各案の詳細（具体的な変更 / 変更前と変更後の動作 / 失うもの / 後から別の案に変える費用 / 選ばれた場合に直ちに行う作業） |
| 7 | 条件付きの推奨（「Xを優先するなら案A」）。2つの基準の推奨で説明が足りる場合は省く |
| 8 | 判断に影響する場合の補足、確認できていない前提と、根拠として読んだ箇所。単純な方法を採れない理由は必要な場合だけここか各案の比較で扱う |
| 9 | この判断の後に決めること |

冒頭では今回実現したい結果を伝え、保存先や実装方法の列挙は、概念と現在・目標の動作を理解した後に示す。テンプレートの項目を埋める順序で説明を決めない。

回答欄を4の直後に置く理由は、比較表と2つの基準の推奨を読んだ時点で決められる読み手が、各案の詳細を読み終えてから回答欄まで戻る必要をなくすためである。

### 各案に必ず書く内容

| 項目 | 書き方 |
|-----|-------|
| 具体的な変更 | どのファイルの何をどう変えるか。「〜な設計にする」ではなく、変更する対象の名前を書く |
| 変更前と変更後の動作 | 外から観測できる動作の変化。動作が変わらない場合は「変わらない」と書く |
| 失うもの | この案を選ぶことで諦める性質。「特になし」と書きたくなった場合は、比較項目が不足している |
| 後から別の案に変える費用 | 後から別の案に変える場合に必要な作業。データ移行が必要か、コードの変更だけで済むか |
| 選ばれた場合に直ちに行う作業 | 回答を受けた後に着手する作業。ユーザーが、決めた後に何が起きるかを予測できるように書く |

## 書かないこと

- **比較のためだけに追加した案。** 検討して除外した案を「公平にするため」に並べない。除外した案に触れる必要がある場合は、除外した理由を1行添えて末尾に書く
- **調査の経緯。** どう調べ、どう考えたかは、判断に影響しない限り書かない
- **独自に作った案の名前。** 「案A / 案B」か、実際の技術名（PostgreSQL 案 / Redis 案）を使う。独自の名前を付けると、読み手はまずその名前の意味を推測しなければならない
- **図と表で同じ情報を2回示すこと。** 構造の違いは図に、項目と `file:line` は表に書く
- **基準を示さない1つだけの推奨。** 推奨は、長期の保守性を優先する基準と、実装コストも考慮する基準の2つで、基準を付けて並べる（Step 5）。どの基準で選んだかが分からない推奨は、判断材料ではなく、特定の案を選ばせるための誘導になる
- **課題の説明を、各案の説明で代用すること。** 各案の説明を読めば課題も分かる、という構成にしない。読み手は課題を理解してから各案を読む（原則2）
- **回答を待たずに実装を進めること。** 判断が必要だと認めた以上、回答を受ける前にどちらかの案で実装を始めない。回答に関係しない作業だけは進めてよい。その場合は、どこまで進めたかを報告する
- 資料のファイルを `git add` すること。作業用のファイルである
