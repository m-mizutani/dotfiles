# ブリーフの JSON と、回答が届く仕組み

`assets/decision-template.html` は、埋め込まれた JSON からページを描画する。編集するのは
JSON だけで、スタイルと描画スクリプトには触れない。

## JSON のフィールド

| フィールド | 型 | 内容 |
|-----------|---|-----|
| `title` | string | ページのタイトル。判断の主題を表す短い名詞句 |
| `question` | string | 決めてほしいことを1文で。「XをAにするかBにするか」の形 |
| `blocked` | string | 決まらないと止まること。止まらないなら、そもそも今聞く判断ではない |
| `context` | string | この分岐が出た理由を1〜3文。調査の経緯ではなく、分岐を生んだ事実 |
| `deadline` | string | 期限や外部制約。無ければ空文字 |
| `figureSvg` | string | inline SVG をそのまま入れる（エスケープせず挿入される）。図が不要なら空文字 |
| `figureCaption` | string | 図の説明。凡例の意味をここで述べる |
| `axes` | array | 判断を分ける軸。`{name, detail}`。3〜5本 |
| `options` | array | 選択肢。下表参照 |
| `recommendation` | object \| null | `{optionId, reason}`。推奨を付けない判断では `null` |
| `conditional` | array | `{priority, optionId}`。「どの軸を優先するならどれか」 |
| `assumptions` | array | `{text, status, evidence}`。`status` は `"確認済み"` か `"未確認"`、`evidence` は `file:line` |
| `dropped` | array | `{label, reason}`。検討して落とした案。無ければ空配列 |
| `later` | array of string | この判断の後に別途決めること |
| `decision` | object | `{optionId, note, at}`。**作成時は `optionId: null` のままにする。** ユーザーがページ上で選ぶとここに書き込まれる |

`options` の各要素:

| フィールド | 内容 |
|-----------|-----|
| `id` | `"a"`, `"b"` など。`recommendation` と `conditional` から参照される |
| `label` | 案の名前。造語を作らず、実際の技術名か「案A」 |
| `summary` | 1文。対比表のヘッダに小さく入る |
| `stance` | 配列。**`axes` と同じ順序・同じ個数**。各軸におけるこの案の位置づけ |
| `change` | 具体的な変更。どのファイルの何がどうなるか |
| `before` / `after` | 外から観測できる挙動。変わらないなら「変わらない」 |
| `cost` | この案で諦めるもの |
| `reversibility` | 後から別案に変えるときに必要になること |
| `next` | これが選ばれた場合に直ちに着手すること |

`stance` の個数が `axes` と合っていないと、対比表のセルが空になる。追加・削除したら
両方を揃え直す。

## 書き方の判断基準

- **`stance` は同じ軸の上の位置づけを書く。** 案の説明を書き直す場所ではない。「その軸で見ると
  この案はどうなるか」だけを短く書く。長くなるなら、それは軸が具体的でない
- **`assumptions` に「未確認」を残すことを避けない。** 確認できなかった前提を消すと、ユーザーは
  確認済みの情報だけを見て判断することになる。未確認と明示されていれば、ユーザーはそこを
  自分で確かめるか、確かめるよう指示できる
- **`figureSvg` は選択肢の違いが構造として現れるときだけ入れる。** 案ごとに別の図を描かず、
  共通の構造を1枚描いて、案によって変わる部分を色と枠線で区別する。テンプレートの
  `--o1` 〜 `--o4` が選択肢の色に対応している（対比表のヘッダと詳細カードで同じ色が使われる）

## 公開のしかた

```
Artifact ツール:
  file_path:     .spec/{slug}/decision-{主題}.html  （spec が無ければ tmp/decision-{主題}.html）
  capabilities:  {"artifact": {}}
  favicon:       初回のみ。絵文字1〜2字
  description:   1文。ギャラリーの副題になる
```

`capabilities` に `{"artifact": {}}` を渡さないと、ページは自分自身を publish できず、
回答欄は「このビューからは回答を記録できません」の表示になる。**回答をページ上で受け取る
設計なので、この宣言は省略できない。**

再公開のたびに `capabilities` を省略すると、保存済みの宣言がそのまま引き継がれる。

## 回答が届く経路

1. ユーザーがページ上で案を選ぶ
2. ページが `claude.use("artifact")` で得た `publish()` を呼び、選択を書き込んだ JSON を含む
   新しいバージョンを公開する
3. artifact を公開したセッションは監視状態に入っているため、この再公開が通知として届く
4. 通知を受けたら `Artifact` ツールの `action: "read"` にその URL を渡してページを読み、
   埋め込まれた JSON の `decision` を確認する
5. 選ばれた案とメモを1行で確認として述べ、その案での作業に入る

監視が働くのは、対話セッション本体が公開した場合に限られる。サブエージェントや
バックグラウンド実行から公開した artifact は通知を受け取れないので、その場合は
ユーザーからターミナルで回答をもらう。

## 回答後にページを直す場合

ページが自分自身を publish した時点で、**ローカルのファイルは公開中の内容より古くなる。**
この状態でローカルファイルから `Artifact` を呼ぶと、ユーザーの回答を上書きする publish に
なるか、競合として拒否される。

回答後に内容を直す必要が出たら、次の順序で行う。

1. `action: "read"` で公開中の内容を取得する
2. その内容を基準に編集する（`decision` の中身は保持する）
3. 同じ `file_path`（または `url`）で公開する

## 回答が届かない場合

ページ上での選択は回答手段の1つであり、必須ではない。ユーザーがターミナルで答えたら
（「artifact は見た、Bで」だけでも）それを回答として扱う。**ページ上での選択を待って
作業を止めない。**

ページ上の回答欄が「このビューからは回答を記録できません」と表示される場合、原因は次のいずれか。

| 原因 | 対処 |
|-----|-----|
| 公開時に `capabilities` へ `{"artifact": {}}` を渡していない | 同じ `file_path` に宣言を付けて公開し直す |
| 閲覧者に編集権限がない（共有先の閲覧のみのユーザー） | ターミナルで回答をもらう |
| サブエージェントやバックグラウンドから公開した | 再公開の通知が届かないので、ターミナルで回答をもらう |

**コメント機能は回答経路にならない。** artifact のコメントを受け付けるのは組織内に共有した
artifact だけで、非公開のままのブリーフでは使えない。加えて、コメントは Claude に送信する
操作をしない限り通知が届かない。回答はページ上の選択かターミナルで受け取る。
