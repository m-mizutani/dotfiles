# 判断依頼ブリーフ作成スキル

ユーザーに決めてもらう事項を1枚の資料にまとめ、そのページ上で回答してもらうスキル。

成果物の価値は、**読み手が調査の経緯を追わずに、分岐点・選択肢の違い・決めた後に起きることを把握し、その場で決められること**にある。読み手が「で、何を決めればいいのか」「この2案はどこが違うのか」を自分で組み立て直す必要が残るなら、その成果物は失敗している。

近い役割のスキルとの違い:

| スキル | 入力 | 出力 |
|-------|-----|-----|
| `brainstorm` | まだ形になっていないアイデア | 実現方法の探索結果。選択肢はここで生まれる |
| このスキル | **選択肢が出そろい、決める段階に来た事項** | 分岐点と選択肢の対比、および回答 |
| `build-review-report` | 済んだ変更 | 検証状況の俯瞰 |

## この成果物でよくある失敗

読み手が求めているのは教育ではなく**回答**である。次の3つはいずれも読み手に作業を残すので、成果物として失敗とみなす。

- **調査の経緯を時系列で並べる。** 読み手が知りたいのは経緯ではなく分岐である。どう辿り着いたかは、判断を変える場合にだけ書く
- **選択肢を独立した説明として並べる。** 案Aの段落と案Bの段落を読ませると、差分を取る作業が読み手に残る。これがこのスキルで最も起きやすい失敗
- **軸を決めずに長所・短所を列挙する。** 案ごとに違う観点で長所短所が挙がっていると、並べても比較にならない

## 中核の原則: 選択肢は同じ軸の上で対比する

**判断を分ける軸を先に決め、すべての選択肢をその同じ軸の上に置く。** 選択肢ごとの説明を書くのは、軸の上の位置づけを示したあと。

軸が揃っていれば、比較は「読む」だけで済む。揃っていなければ、読み手はまず各案の記述から軸を抽出する作業から始めることになり、それはこちらがやるべき仕事である。

軸の条件:

- **選択によって実際に結果が変わるものだけを軸にする。** どの案でも同じになる項目は軸ではない。書けば紙面が増えるだけで、判断は1ミリも進まない
- **3〜5本に収める。** 軸が10本あるのは、軸を絞る作業をしていないということ
- **軸には、何がどう変わるのかを具体的に書く。** 「保守性」「拡張性」のような語だけでは、読み手はどちらが良いのか判断できない。「新しい通知先を追加するときに変更が必要なファイル数」のように、観測できる形にする

## 使うとき・使わないとき

| 状況 | 対応 |
|-----|-----|
| 選択肢の違いを1文で言い切れて、後から変えるのも容易 | このスキルを使わず `AskUserQuestion` |
| 選択肢が複数あり、後戻りコストが大きい（アーキテクチャ・データモデル・外部契約・セキュリティ・永続化スキーマ） | このスキルを使う |
| 判断材料が長く、選択肢の対比に表や図が要る | このスキルを使う |
| 手元の根拠がすでに結論を決めている | 決めて進み、そう判断した理由を1行で報告する。均衡のために選択肢を並べない |
| ユーザーが既に方向を示している | その方向の中で進める。選ばれなかった案を再提示しない |
| 4つの一行（何が問題か / 具体的な変更 / before → after の挙動 / 主な欠点）をまだ埋められない | 調査を続ける。埋まらない案は提案ではない |

自発的に発動してよいが、**判断1件につき1枚**に留める。細かい選択のたびに artifact を作るとユーザーの確認コストのほうが高くつく。

## 進め方

### Step 1: 分岐点を1文にする

「何をどう決めるのか」を1文で書けるまで、artifact を作り始めない。書けないなら、まだ分岐点が特定できていない。

- 良い: 「セッション情報の保存先を PostgreSQL のテーブルにするか、Redis にするか」
- 悪い: 「セッション管理の設計方針」（何を選ぶのかが書かれていない）

未決事項が複数絡んでいる場合は、依存関係を確認して**先に決めるべき1件**を主題にする。後続の判断は「これを決めた後に別途決めること」として末尾に列挙するに留める。複数の判断を1枚に詰めると、どれについての回答なのかが曖昧になる。

あわせて、**決まらないと何が止まるのか**を特定する。止まらないなら、それは今ユーザーに聞くべき判断ではない。

### Step 2: 各選択肢の根拠を実際のコードで確認する

選択肢の記述は、実際のコード・spec・依存ライブラリのドキュメントで裏を取ってから書く。記憶や一般論で書いた選択肢は、ユーザーがそれを選んだ時点で破綻する。

最低限、各選択肢について次を確認する。

- その変更が触るファイルと、影響を受ける呼び出し元（`file:line` で示せる状態にする）
- 同種の処理がリポジトリ内に既にあるか。ある場合、それは意図的なパターンか
- そのリポジトリの `CLAUDE.md` / `.claude/rules/` に、この判断を縛る規定があるか
- 外部ツール・ライブラリの設定に関わる場合、**使用中のバージョンの公式ドキュメント**での挙動

確認できなかった点は消さずに、Step 5 の「確認できていない前提」として artifact に残す。

### Step 3: 軸を抽出する

選択肢の説明を書く前に軸を決める。「中核の原則」の条件を満たす軸を3〜5本。

軸を決めた結果、**どの軸でも差がつかない選択肢**が出てきたら、それは選択肢ではない。落とす。

### Step 4: 推奨を付けるかを決める

| 判断の種類 | 扱い |
|----------|-----|
| 命名・表記・UI の文言・ファイル配置など、好みの問題 | 推奨を明示してよい |
| アーキテクチャ・セキュリティ・データモデル・外部契約・永続化 | **推奨ラベルを付けない**。ユーザーの判断であり、こちらが先に結論を出すと判断材料の提示ではなく誘導になる |

推奨を付けない場合も、読み手を放り出さない。**「どの軸を優先するならどれになるか」の条件付き対応**を書く。「読み取り性能を優先するなら A、運用対象を増やしたくないなら B」の形であれば、判断を奪わずに材料を示せる。

### Step 5: artifact を作る

1. `artifact-design` skill を読み込む（Artifact の設計指針。省略しない）
2. `assets/decision-template.html` を作業ディレクトリにコピーする
   - spec がある場合: `.spec/{slug}/decision-{主題}.html`（slug はブランチ名の slash 以降）
   - spec がない場合: `tmp/decision-{主題}.html`（リポジトリルート直下の `tmp`）
3. テンプレート内の `BRIEF` JSON を書き換える。**編集するのは JSON だけ**で、スタイルと描画スクリプトには手を入れない。ページはこの JSON から描画され、回答もこの JSON に書き戻される
4. `Artifact` ツールで公開する。`capabilities` に `{"artifact": {}}` を必ず渡す（これがページ上で回答を記録するための宣言）。初回は `favicon` も渡す
5. ターミナルには**要約1〜3行と URL、そして「何を決めてほしいか」の1文**だけを書く。artifact の内容をターミナルに再掲しない

JSON の各フィールドの意味と、回答がどう届くかは `references/answering.md` を読む。

図を入れる場合の制約:

- **図は選択肢の違いが構造として現れるときだけ入れる。** データの流れ・責務の境界・呼び出し関係が案によって変わる場合が該当する。差が設定値や依存の有無だけなら、図は表の劣化版にしかならない
- **1枚に重ねる。** 案ごとに別の図を描くと、読み手が2枚を見比べて差分を取る作業が発生する。共通の構造を1枚描き、案によって変わる部分だけを色と枠線で区別する
- inline SVG または HTML+CSS で描く。mermaid と ASCII Art は使わない
- 凡例を必ず添える。theme-aware にする（トークンはテンプレートに定義済み）

### Step 6: 回答を受け取って続行する

ページ上で選択されると、ページ自身が新しいバージョンを publish する。公開時にこのセッションは監視状態に入っているため、republish の通知が届く。

1. 通知を受けたら `Artifact` ツールの `action: "read"` で当該 URL を読み、`BRIEF` JSON の `decision` を確認する
2. 選ばれた案と、添えられたメモを1行で確認として述べ、その案での作業に入る
3. ユーザーがターミナルで直接答えた場合は、それを回答として扱う。ページ上での選択を待たない

ローカルのファイルは republish によって古くなっている。**再公開が必要になったら、ローカルファイルから publish せず、まず `action: "read"` で公開中の内容を読んでから編集する。**

## artifact の構成

上から順に、読み手が読むのをやめてよい地点が下がっていく順に並べる。

| 位置 | 内容 |
|-----|-----|
| 1 | 決めること（1文）、決まらないと止まること、締め切りや制約 |
| 2 | 軸 × 選択肢の対比マトリクス。構造が変わる場合はここに図を1枚 |
| 3 | 回答欄（各案を選ぶ操作とメモ欄） |
| 4 | 各選択肢の詳細（具体的な変更 / before → after / 失うもの / 後戻りコスト / 選ばれた場合に直ちにやること） |
| 5 | 条件付きの対応（「Xを優先するなら案A」） |
| 6 | 確認できていない前提と、根拠として読んだ箇所 |
| 7 | この判断の後に別途決めること |

回答欄を2の直後に置くのは、対比マトリクスを見た時点で決まる読み手を、詳細まで読ませてから戻らせないため。

### 各選択肢に必ず書くこと

| 項目 | 書き方 |
|-----|-------|
| 具体的な変更 | どのファイルの何がどうなるか。「〜な設計にする」ではなく、変更対象を名指しする |
| before → after | 外から観測できる挙動の変化。挙動が変わらないなら「変わらない」と書く |
| 失うもの | この案を選ぶことで諦める性質。「特になし」と書きたくなったら、軸の抽出が足りていない |
| 後戻りコスト | 後から別の案に変えるときに何が必要か。データ移行が要るのか、コードの差し替えだけで済むのか |
| 選ばれた場合に直ちにやること | 回答後にこちらが着手する内容。ユーザーが「決めた後どうなるか」を予測できる状態にする |

## やらないこと

- **均衡のための選択肢の水増し。** 検討して落とした案を「公平のため」に並べない。落とした案に触れる必要があるなら、落とした理由を1行添えて末尾に置く
- **経緯の再現。** どう調べてどう考えたかは、判断を変えない限り書かない
- **選択肢に造語で名前を付けること。** 「案A / 案B」か、実際の技術名（PostgreSQL 案 / Redis 案）を使う。独自の呼称を作ると、読み手はまず用語の解読から始めることになる
- **同じ情報を図と表で二重に出すこと。** 構造の違いは図、項目と `file:line` は表
- **アーキテクチャ・セキュリティ・データモデルの判断に推奨ラベルを付けること**（Step 4）
- **回答を待たずに実装を進めること。** 判断が要ると認めた以上、回答前に片方の案で書き始めない。回答に依存しない部分だけは進めてよく、その場合はどこまで進めたかを述べる
- artifact ファイルを `git add` すること。作業用の成果物である
