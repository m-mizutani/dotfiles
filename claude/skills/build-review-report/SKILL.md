# 変更レビューレポート作成スキル

変更（PR / ブランチの差分 / 未コミット変更）について、次の3つの問いに答えるレポートを作る。

1. **何がどう変わったか** — 観測できる挙動の before → after
2. **その変更は何を検証すべきだったか** — 変更の性質と spec から導出される要求
3. **その検証は届いているか** — 届いている範囲、意図的に見送られた範囲、届いていない範囲

このレポートの価値は、**読み手がテストコードを1本も開かずに、変更を信頼してよいかを判断できること**にある。テスト関数名の一覧やカバレッジ数値を並べても、読み手は結局コードを読み直すことになるので、それは失敗した成果物とみなす。

`my-code-review` / `codex-review` は個別の指摘を出すスキル、これは**判断材料となる俯瞰資料を作る**スキル。役割が違うので、指摘の列挙で紙面を埋めない。

## 認知負荷の設計がこのスキルの本体

読み手は「大量のテストコードを読みたくない」からこのレポートを求めている。文章と表を並べただけの成果物は、読む量を減らしただけで**読解の労力は減らない**（読み手が頭の中で対応付けをやり直すことになる）。

だから次の2つを最優先する。

- **第1層は図を主役にする。** 文章は図の添え書きとして数行に留める。構造・分布・対応関係は、文章より図のほうが少ない労力で伝わる
- **1枚の図に、対応付けが必要な情報を重ねる。** 「変更箇所の図」と「検証状態の図」を別々に出すと、読み手が2枚を見比べて対応付ける作業が発生する。同じ図の上に、変更箇所を枠線で、検証状態を塗りで重ねれば、その作業が消える

図の具体的な設計は `references/diagrams.md` を読む。レポート生成前に必ず参照する。

## レポートの階層

各層は下層の要約であり、**第1層だけ読んで判断でき、必要なときだけ下に降りられる**関係を保つ。

| 層 | 内容 | 主な形式 | 読み手の目的 |
|---|-----|---------|------------|
| 第1層 | 総括 + 変更と検証状態を重ねた図 | **図（主役）** + 各3〜5行の文章 | 変更を信頼してよいかの判断 |
| 第2層 | 挙動の変化（before → after） | 対比表 | 何が変わったかの確認 |
| 第3層 | 要求される検証 ↔ 実テストの突合 | マトリクス | どの検証が届いているか |
| 第4層 | 未充足・見送りの詳細 | `file:line` 付きリスト | 着手 |

第1層に置く文章は、3つの問いに対する各3〜5行の要約。書き方は次の水準を満たす。

- **何が変わったか** — 差分の要約ではなく、観測できる挙動の変化として。「実装を変更した」ではなく「入力 A に対する戻り値が B から C に変わった」
- **検証が届いている範囲** — 個別のテスト内容ではなく、**このテスト群が通ることで何を信じてよいかの範囲**の宣言。例：「主要な正常系は戻り値の値まで検証されている。異常系はエラーが返ることまでで、エラーの種別は検証されていない。外部APIはすべてモックで、実際のAPIが期待通り応答することは確認されていない」
- **届いていない範囲** — 点の列挙ではなく傾向として。「並行実行時の振る舞いは全領域で見送られている」「統合テストは記述されているが build tag により CI では実行されていない」

## 進め方

### Step 1: 対象の確定

```bash
git branch --show-current
git status --porcelain
git log --oneline -15
git symbolic-ref --quiet refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@'
```

| 状況 | 対象 |
|------|-----|
| feature branch にいる | default branch との merge-base からの差分 ＋ 未コミット分 |
| default branch にいて未コミット変更がある | staged + unstaged |
| PR 番号・ブランチ名・パスが引数で指定された | それに従う |

```bash
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git diff --stat "$BASE"...HEAD
git diff "$BASE"...HEAD
git diff HEAD
```

範囲は原則こちらで決めて、レポート冒頭に明示する。判断が結果を大きく変える場合のみ `AskUserQuestion` で確認する。

差分が数十ファイルを超える場合は、Agent（Explore）に領域を分けて読ませて要約させ、main context を軽く保つ。1体で足りるなら1体に留める。

### Step 2: 変更の読み取り — 挙動の変化として書く

**差分の hunk をそのまま要約してはいけない。** 差分は変更行しか映さないので、それを言い換えても読み手の理解は進まない。必要なのは「外から観測して何が変わったか」で、これがそのまま Step 3 の検証項目に変換できる。

最低限、変更されたファイルの全体、変更された関数・型の呼び出し元と呼び出し先、同種処理の既存実装パターン、そのリポジトリの `CLAUDE.md` / `.claude/rules/` を読む。

記述の水準：

- ❌ 「`auth.Verify` の実装を変更し、キャッシュ機構を追加した」
- ✅ 「`auth.Verify` は同一トークンの2回目以降の呼び出しで外部への検証要求を行わなくなった（`auth.go:88`）。結果として有効期限切れの検知が最大60秒遅れる」

- ❌ 「エラーハンドリングを改善した」
- ✅ 「`store.Save` は一意制約違反時に、これまで `*pgconn.PgError` をそのまま返していたが、`ErrDuplicate` に変換して返すようになった（`store.go:120`）。呼び出し元 `handler.PostSession:45` はこの新しいエラー型で分岐する」

挙動の変化として書けない差分は、**挙動を変えない変更（リファクタリング）**である。これは別扱いにする（Step 3 参照）。混ぜると「変更したのにテストがない」と「変更していないので既存テストで足りる」の区別がつかなくなる。

あわせて、**変更されていないが影響を受ける箇所**を特定する。呼び出し元、共有される状態、同じスキーマを読む別の経路。ここは差分に現れないため、明示的に探さないと漏れる。

### Step 3: 要求される検証の導出

ここがレポートの中核。導出の根拠は2系統あり、両方を使う。

#### 系統A: 変更の性質から導出する

変更の種類ごとに、要求される検証が決まる。

| 変更の種類 | 要求される検証 |
|----------|-------------|
| 機能の追加 | 正常系、異常系、境界値 |
| 既存挙動の変更 | 新しい挙動の検証、および旧挙動に依存していた箇所の追随 |
| 挙動を変えないリファクタリング | 変更前の挙動を固定するテストが**変更前から存在していたか** |
| バグ修正 | 修正前には失敗し、修正後に成功するテスト（リグレッションテスト） |
| 公開インターフェースの変更 | 全呼び出し元の追随、後方互換性 |
| 永続化スキーマの変更 | マイグレーション、既存データの読み取り、ロールバック |
| 依存の追加・更新 | その依存が期待通り応答すること（モックでは代替にならない） |
| 削除 | 削除対象に依存していた経路が残っていないこと |
| 設定・環境変数の追加 | 未設定時の挙動、不正値の扱い、デフォルト値 |

「挙動を変えないリファクタリング」の行には注意が必要。`CLAUDE.md` の Design Fidelity は、挙動を保つべき変更の前にその挙動を固定するテストがあるか確認するよう規定している。**テストが変更と同時に追加された場合、変更前の挙動を保証したことにはならない**（新しい実装に対して新しい期待値を書いただけになる）。この判定には差分だけでは足りないので、コミット順序を確認する。

```bash
git log --oneline --follow -- path/to/test_file
git log -S "TestFuncName" --oneline -- path/to/test_file
```

#### 系統B: spec から導出する

`.spec/{slug}/spec.html`（または `spec.md`）があれば、次の節から要求を抽出する。slug はブランチ名の slash 以降。

| spec の節 | 抽出する要求 |
|----------|-----------|
| 1. 要件定義 / 機能要件・非機能要件 | 各要件が満たされることの検証 |
| 2. 設計 / エラーハンドリング・境界条件 | 列挙された異常系・境界値・並行時の振る舞い、返すエラー型/コード |
| 2. 設計 / 外的インターフェース | API・公開シグネチャ・設定・環境変数・CLIフラグ・スキーマ/マイグレーション |
| 2. 設計 / データフロー | 主要ユースケースの通し検証 |
| 3. 実装計画 / テスト計画 | 計画された各テストと、その進捗（`task todo` / `task done`） |

**「何が見送られたか」の一次情報源は spec のテスト計画である。** 進捗が `task todo` / `task done` で管理されているため、次の3つが機械的に判別できる。これはテストコードを読むだけでは絶対に得られない情報なので、spec があるときは必ず確認する。

- `done` なのに対応するテストが見つからない → 完了扱いの誤り
- `todo` のまま残っている → 意図された見送り、または未着手
- テスト計画に記載のない要求 → spec 作成時点での見落とし

```bash
ls .spec/*/ 2>/dev/null
grep -o 'class="task [a-z]*"' .spec/{slug}/spec.html | sort | uniq -c
```

spec が無い場合は系統A のみで導出し、レポートにその旨（導出根拠が変更の性質のみであること）を明記する。spec は git 管理外のため、過去タスクの spec は残っていないのが通常。

導出した各項目には**根拠を必ず付ける**（変更の性質由来か、spec のどの節由来か）。根拠のない要求は読み手が判断できない。

### Step 4: 実テストとの突合

Step 3 で導出した各要求について、対応するテストを探して状態を判定する。

| 状態 | 判定基準 |
|-----|---------|
| ✅ 検証済み | 期待値を値まで検証していて、挙動が壊れたときに落ちる |
| ⚠️ 弱い | テストは存在するが、壊れても落ちない可能性がある（エラーの有無だけ見て型を見ていない、戻り値の一部しか見ていない、モックの呼び出し回数だけ見ている） |
| ⏭️ 見送り | 明示的な判断がある（spec のテスト計画 `todo`、`t.Skip`、build tag、環境変数ガード、TODO コメント） |
| ❌ 欠落 | 要求があるのに対応するテストがない |

判定の基準は一貫して「**この検証があることで、挙動が壊れたときに落ちるか**」に置く。カバレッジの数値は使わない。行が実行されることは、挙動が検証されていることを意味しない。

**⚠️ と ❌ を分ける理由**、および **⏭️ と ❌ を分ける理由**は、読み手が取る行動が違うため。⚠️ はテストが存在するので見つけにくく、❌ より危険なことがある。⏭️ は判断済みなので確認が要るだけ、❌ は判断されていないので決定が要る。

あわせて、**テストは実際に実行されるのか**を確認する。実行されないテストは検証していないのと同じなので、build tag、環境変数、`t.Skip`、CI 設定を確認する。

```bash
grep -rn "t.Skip\|testing.Short()" --include="*_test.go" .
grep -rn "^//go:build" --include="*_test.go" .
ls .github/workflows/ && grep -rn "go test\|npm test" .github/workflows/
```

外部依存（外部API、DB、SaaS、決済など）と不確定要素（時刻、乱数）については、モックのみで検証されているかを判定する。モックは自分が書いた期待を検証するだけで、相手が本当にその通り振る舞うことは保証しないため、実接続の通し確認があるかを別項目として扱う。

### Step 5: レポートの生成

**HTML で作成し、`Artifact` ツールで公開する。** 図を主役にする設計上、inline SVG と CSS で描いた図が必要になるため、この媒体を選ぶ。ターミナル上の Markdown では図が描けず、このスキルの目的（認知負荷の軽減）を達成できない。

手順：

1. `references/diagrams.md` を読み、変更の形に合った図を選ぶ
2. `artifact-design` skill を読み込む（Artifact の設計指針。省略しない）
3. `assets/report-template.html` を出発点に、`.spec/{slug}/review-report.html` を作成する（spec が無い場合は `tmp/review-report.html`）
4. `Artifact` ツールに `file_path` としてそのパスを渡して公開し、URL をユーザーに提示する
5. 修正したら**同じ `file_path`** で `Artifact` を呼び直し、同一URLへ再デプロイする

図の実装上の制約：

- **mermaid は使わない。** 検証状態を色で重ねる、変更箇所を枠線で示すといった表現が必要で、それには inline SVG または HTML+CSS のほうが適する。`spec` skill も同じ方針を採っている
- ASCII Art は使わない
- 図は theme-aware にする（ライト・ダーク両方で読める配色。トークン定義はテンプレートに含まれている）
- 凡例のない図は置かない。色と枠線の意味が読み手に伝わらなければ、図は認知負荷を上げるだけになる

レポートファイルは `git add` しない。作業用の成果物である。

## 図の設計原則

`references/diagrams.md` に実装パターンを置いているが、判断の基準はここに書く。

- **図は主張を1つだけ運ぶ。** 1枚に3つの主張を詰めると、読み手はまず「この図は何を言っているのか」を解読する作業から始めることになる
- **同じ情報を図と表で二重に出さない。** 分布・構造・対応関係は図、個別の項目と `file:line` は表。役割を分ける
- **対応付けが必要な情報は重ねる。** 変更箇所と検証状態は、別々の図ではなく1枚に重ねる（枠線と塗りで別の次元を表現する）
- **図の枚数を増やさない。** 第1層は原則2枚（構造を示す1枚、分布を示す1枚）。認知負荷の軽減が目的なので、図の乱用は逆効果になる
- **描けない図を無理に描かない。** 変更が単一関数に閉じていて構造図が描けない場合は、入力条件と出力の対応表に状態を色で重ねる形に替える。`references/diagrams.md` の選択基準に従う

## やらないこと

- **個別の指摘の列挙。** 実装の良し悪しの評価は `my-code-review` / `codex-review` の役割。このスキルは判断材料を提示する
- **テストの追加・修正。** レポートを見たユーザーが判断する。求められたら別途対応する
- **カバレッジ計測ツールの実行結果をそのまま貼ること。** 行カバレッジは「挙動が検証されているか」を答えないため、レポートの主役にはしない。補助情報として使うのは構わない
- **紙面の水増し。** 読み手の判断を変えない項目は載せない。特に「要求なし」の箇所を欠落のように見せてはいけない
