# spec実装 + レビュー指摘対応 + PR作成

specを実装し、実装内容がspecの要求事項・基本設計・提示されたデザインを満たしていることを照合し、`/codex-review`（使えない場合は `/code-review`）の指摘を片付け、PRを作成するまでを1つの作業とする。

**このスキルで最も多い失敗は、specに書かれた項目の実装漏れである。** 「一通り実装した」という感触は完了の根拠にならない。4. の照合を実施し、要求事項・基本設計の各項目に対応する実装の実体を示せることが完了の条件である。

# 0. 最初に完了条件を `.spec/goal.md` に書く

実装に着手する前に、このスキルの完了条件を `.spec/goal.md` に書き出す。このファイルは Stop hook が毎ターン終了時に読み、未達の条件があれば作業を押し戻すために使われる。ユーザーに `/goal` を実行させる必要はない。

以下をそのまま `.spec/goal.md` として書く。

```markdown
# 完了条件

- [ ] specの全タスクがdoneになっている
- [ ] specの「1. 要求事項」の全項目について、それを満たす実装の実体（file:line / 識別子 / テスト名）を対応づけられている
- [ ] specの「2. 基本設計」の全項目（構成要素と責務境界・データモデル・状態の持ち方・主要ユースケースの流れ・エージェントのワークフロー・画面の要件と概要）が設計どおりに実装されている
- [ ] 提示されたデザインを全画面・全状態について再現している（デザインの提示がない場合は「該当なし」と明記する）
- [ ] プロジェクトの検証ゲート（テスト/lint）が通っている
- [ ] codex-review（使えない場合はcode-review）を実行した
- [ ] レビューの全指摘が「確信が強い→修正または却下済み」「確信が弱い→修正のうえ論点と判断理由を報告済み」「判断が必要→保留してユーザーに選択肢を提示済み」のいずれかで処理されている
- [ ] 変更がcommit・pushされ、PR（判断が必要な指摘が残っていればdraft）が作成されている
- [ ] そのPRのCIが通っている
- [ ] 照合結果・3区分の報告・PRのURLを出し終えている
```

書いたら、その内容をユーザーに1〜2文で伝えてそのまま 1. へ進む。承認を待って手を止めない。

`.spec/` はグローバルの gitignore に入っているため、このファイルはcommit対象にならない。

## 1. と 2. を終えた時点で追記する

spec を特定し（1.）、PRの分割単位を決めた（2.）ら、`.spec/goal.md` に次を追記して条件を具体化する。

- **spec の実体パス**（例 `.spec/{slug}/spec.html`）。1行目の条件をこのパスで書き換える
- **要求事項の展開**。specの「1. 要求事項」に列挙された機能要件・非機能要件を、**1件1行のチェックボックスに展開して書き出す**。「全項目」という総称のままにしない。ここで展開した行が、4. の照合で1件ずつ潰す対象になる
- **基本設計の展開**。specの「2. 基本設計」に書かれた項目のうち、実装の有無が外から判別できるもの（データモデルの変更、状態の持ち方、主要ユースケースの流れ、画面ごとの状態など）を同様に1件1行で書き出す
- **デザインの所在**。デザインが提示されている場合、その所在（ファイルパス / URL / 会話中の画像 / specの画面セクション）を書き、再現対象の画面と状態を1行ずつ書き出す。提示がない場合は「デザインの提示なし」と明記する
- **この spec 固有の検証**。specの「4. テスト計画」から、通すべき検証（統合テスト、マイグレーションの適用確認など）を条件として1件1行で足す
- **PRの本数**。2. で分割した場合は「PRを{N}本に分割し、全PRについて上記を満たして全PRのURLを報告し終えている」を足す

要求事項が多くて行数が増えても、まとめて1行に畳んではならない。畳んだ時点で実装漏れが検出できなくなる。

PRを分割する場合、完了は1本目のPRではなく**分割した全PRの完了**を指す。1本ずつ書き換えるのではなく、最初から全PRを含む形で書く。

引数の指示を実装対象とする場合（1. の「specが見つからない場合」）は、spec関連の条件を落とし、代わりに引数の指示の内容を1件1行で条件として書く。

# 1. specを特定する

specは **これまでの会話で作成・合意したもの** を指す。原則 `Artifact` として公開済みで、実体は `.spec/{slug}/spec.html` にある。

- 引数でファイルパスやArtifactのURLが与えられた場合はそれをspecとみなす
- 会話中にspecがある場合はそれを使う（`Artifact` を再デプロイするために、実体のローカルパスを必ず押さえておく）
- 会話にspecがない場合は、branch名のslash以降をslugとして `.spec/{slug}/spec.html` を探す
  - 例: branch `feat/hybrid-vectorizer` なら slug は `hybrid-vectorizer`
  - `spec.html` がなければ `.spec/{slug}/spec.md`、それもなければ `.cckiro/specs/{slug}/` 以下のmarkdown

specを特定したら、**「1. 要求事項」と「2. 基本設計」を通読する**。実装計画（6章）だけを読んで着手してはならない。実装計画は手順であって、満たすべき条件の一覧ではない。

## デザインの所在を確認する

specの特定と同時に、**デザインが提示されているかを確認する**。次のいずれかがあればデザインの提示があるものとして扱う。

- ユーザーが会話中に貼った画面イメージ・モックの画像
- デザインファイルやモックのURL・パス（Figmaのリンク、HTMLモック、`design` skill で作ったキャンバスなど）
- specの「2. 基本設計 → 画面の要件と概要」および「5. 詳細設計」に書かれた画面仕様
- 既存画面のスクリーンショットを基準として示された場合

提示があれば、その所在を `.spec/goal.md` に記録し（0. の追記）、4. で再現を照合する。**「デザインがあったことを忘れて実装だけ進める」ことがないよう、着手前に必ず所在を固定する。**

## specが見つからない場合、または引数で明示的に指示された場合

次のどちらかに当てはまるなら、**引数に書かれた指示そのものを実装対象とする**。specファイルの作成は求めない。

- 上のどこにもspecが見つからず、かつ引数に実装内容の指示がある
- specの有無にかかわらず、ユーザーが引数の内容を実装するよう明示的に指示している（例: `/implement 引数の内容をやって`、specを参照せず具体的な変更内容を引数で渡してきた場合）

このとき:

- 引数の指示を実装対象として扱い、3. 以降のspec関連の手順（進捗チェックボックスの更新、`Artifact` の再デプロイ）は該当しないので飛ばす。それ以外の手順（全て実装しきる、4. の照合を引数の指示に対して行う、検証ゲートを通す、5. のレビューを実行して3区分で処理する、PRを作成する）はそのまま適用する
- 引数の指示が曖昧で複数の解釈ができる場合は、実装に入る前にユーザーに確認する
- 引数の範囲を超える設計変更が必要になったら、黙って実装せずユーザーに判断を仰ぐ

specも引数の指示もどちらも無い場合は実装に入らず、`spec` skill の Phase 1（spec作成）へ回す。

# 2. PRの分割単位を決める

specや合意した計画が変更を複数のPRに分けることを求めている場合、あるいは変更量・依存関係から分けると判断した場合は、実装に着手する前に**分割単位とマージ順**を確定させる。

- 各PRについて「含める変更」「依存する先行PR」を1行ずつ書き出し、ユーザーに提示してから実装に入る
- 分割は stacked PR にする。2本目以降は直前のPRのブランチをbaseにして作成する（`gh pr create --base <先行PRのブランチ>`）。default branchから並列にPRを立てない
- 各PRの本文に、スタック内での位置・base branch・スタック全体のマージ順を書く

**分割した場合、このスキルの完了は「分割した全PRが作成され、それぞれのCIが通っている」ことを指す。** 1本目のPRを作った時点で止まってはならない。3.〜7. の手順をPRごとに最後まで回し、全PRを終えてから 8. の報告をまとめて行う。

- 途中のPRで「判断が必要」な指摘が出た場合は、そのPRをdraftのままにして論点を記録し、**次のPRの実装に進む**。ユーザーの判断待ちを理由に残りのPRを未着手で放置しない
- 先行PRがまだmergeされていなくても、そのブランチをbaseにして次のPRを進める。mergeを待って手を止めない
- 実装に支障をきたす問題（ユーザーの判断なしには先へ進めない設計上の分岐など）が起きた場合のみ止まる。その場合も、止まった理由と残りのPRの状況を明示して報告する

要求事項や画面を複数PRに分割する場合、**どの要求事項をどのPRで満たすかを対応づけて書き出す**。分割の境界で要求事項が抜け落ちるのが典型的な実装漏れの経路である。

分割が不要（PR1本）な場合は、以降の手順をそのまま1回だけ実行する。

# 3. specを全て実装する

- 実装計画のステップ順に、specに書かれた内容を**全て**実装する
- 進捗チェックボックスは都度書き換える（HTMLなら `<li class="task todo">` → `<li class="task done">`、markdownなら `- [ ]` → `- [x]`）。最後にまとめてではなく、作業が終わるたびに実施する
- チェックを埋めると同時にspecを読み直し、実装すべき内容と方向性を確認する
- specを書き換えたら、同じ `file_path` で `Artifact` を呼び直して公開中のspecを最新化する（URLは変えない）
- 実装中に追加の指示があった場合もspecを更新する
- `// TODO` / `// FIXME`、仮実装、スタブを残さない
- specに書かれていない設計変更（特に永続化スキーマの変更）が必要になったら、黙って実装せずユーザーに判断を仰ぐ
- 実装に支障をきたす問題が発生しない限り、最後まで完了させよ。途中で止まるな
- 実装が一通り終わったら、プロジェクトの検証ゲート（テスト・lint など）を実行して通す

**実装計画の全ステップを終えても、それは「実装完了」ではない。** 実装計画は spec を書いた時点での手順の見立てであり、要求事項を網羅している保証はない。検証ゲートを通したら、そのまま 4. の照合に進む。

# 4. 要求事項・基本設計・デザインと実装を照合する

specがある場合（引数の指示を実装対象とする場合はその指示に読み替える）、**この照合を実施するまで実装は完了していない**。省略してはならない。

## 照合のやり方

- specの「1. 要求事項」「2. 基本設計」を**もう一度開いて読む**。記憶や実装中の印象で判断してはならない
- 各項目について、それを満たす実装の実体を **`file:line` / 識別子 / テスト名** で示す。示せない項目は未実装である
- 「実装したはず」「対応済みのつもり」は根拠にならない。該当コードを実際に読んで確認する
- 検証ゲートが通っていることは、要求事項を満たしている根拠にならない。テストが存在しない要求事項は検証ゲートを通っても未実装でありうる

## 照合表を作る

照合結果を次の形で書き出す。これは 8. の報告にそのまま載せる。

| spec の項目 | 章 | 実装の実体 | 状態 |
|---|---|---|---|
| [要求事項の1項目をそのまま引用] | 1. 要求事項 | `path/to/file.go:120` の `FuncName` / テスト `TestXxx` | 実装済み |
| [基本設計の1項目] | 2. 基本設計 | ... | 未実装 |

「実装済み」以外の状態（未実装・部分的・設計と異なる）が1件でも残っているなら、**3. に戻って実装する**。残したまま 5. 以降へ進んではならない。

## デザインの再現を照合する

1. でデザインの提示を確認している場合、**そのデザインの完全な再現を完了条件とする**。次の各点をデザインと実装で1つずつ突き合わせる。

- **要素の構成と並び順**: デザインにある要素がすべて存在し、順序と階層が一致しているか。デザインにない要素を勝手に足していないか
- **レイアウト**: 配置、整列、幅・高さの関係、余白の取り方
- **文言**: ラベル、見出し、プレースホルダ、エラーメッセージ、空状態の文言を**そのまま**再現しているか。要約したり言い換えたりしていないか
- **視覚スタイル**: 色、タイポグラフィ（サイズ・太さ・行間）、角丸、境界線、影
- **状態の網羅**: デザインに示された全状態（初期表示 / ローディング / 空 / エラー / 選択中 / 無効 / ホバー・フォーカス）を実装しているか
- **レスポンシブとインタラクション**: 画面幅ごとの変化、遷移、アニメーションの有無

判定基準は「完全な再現」である。**「概ね同じ」「近い見た目」は未達として扱う。** 差分は1件ずつ列挙し、実装で埋める。

可能な限り、実際に描画して確認する。アプリを起動して画面を表示できるなら `run` skill を使い、スクリーンショットとデザインを突き合わせる。起動できない場合は、デザインのソース（モックのHTML/CSS、画像、spec の画面セクション）と実装のマークアップ・スタイルを要素単位で読み比べ、その方法で確認したことを報告に明記する。

再現できない差分（デザインシステムの制約、技術的に不可能な表現、デザイン側の指定が曖昧など）がある場合は、勝手に近い表現へ置き換えて済ませず、**差分の内容と理由を 6. の「判断が必要」に回してユーザーに提示する**。

## 照合で差分が見つかったときの扱い

| 差分の性質 | 対応 |
|---|---|
| 単に実装していない / 実装が足りない | 3. に戻って実装する。ユーザーに報告して終わりにしない |
| specの記述が実装と食い違い、どちらが正しいか自明 | 正しい側に合わせ、specを更新して `Artifact` を再デプロイする |
| specの記述どおりに実装すると別の要求と矛盾する、または設計判断が必要 | 実装を止めて 6. の「判断が必要」として扱い、選択肢をユーザーに提示する |

**要求事項を勝手に縮小して「満たした」ことにしてはならない。** 実装できない要求があるなら、それを明示してユーザーの判断を仰ぐ。

# 5. レビューを実行する

`codex-review` skill を引数なしで起動し、この実装の差分をレビューさせる。

> このスキルの中では、`codex-review` の Step 6 にある「修正プランを提示してユーザーの承認を待つ」は適用しない。承認を待たず、6. の仕分けに従って自分で処理を進める。ただし Step 5 の「指摘された箇所を実際に読んでから採否を判断する」は必ず守る。

## `codex-review` が使えない場合は `code-review` にフォールバックする

`codex-review` は `mcp__codex__codex` に依存するため、Codex の MCP サーバーが接続されていないセッションでは実行できない。次のいずれかに当たったら、組み込みの `code-review` skill に切り替える。

- 利用可能な skill の一覧に `codex-review` がない
- `mcp__codex__codex` が利用可能なツールに含まれていない
- `codex-review` を起動したが `mcp__codex__codex` の呼び出しがエラーで失敗する

切り替えるときの扱い:

- `code-review` skill を引数なしで起動する。`--fix` は付けない（指摘の採否は 6. の仕分けで自分が判断する）
- 「`codex-review` が使えないため `code-review` でレビューした」ことをユーザーへの報告に明示する
- 6. 以降の手順（3区分の仕分け、修正、commit・push・PR作成、CI確認）はそのまま適用する

**レビューが実行できないことを理由に 6. 以降を飛ばしてはならない。** 両方とも使えない場合は、その事実を明示したうえで自分で差分と周辺コードを読んでレビューし、同じ3区分で処理する。

# 6. 指摘を確信度で3つに仕分ける

指摘された `file:line` と周辺（呼び出し元・呼び出し先・既存のテスト）を**実際に読み**、`CLAUDE.md` / `.claude/rules/` / spec に照らしてから仕分ける。記憶や一般論で分類してはならない。

| 区分 | 該当条件 | 対応 |
|------|---------|------|
| **確信が強い** | 読んで指摘が事実だと確認でき、修正内容も一意に決まる。あるいは読んだ結果、誤指摘・既に対処済みだと確認できた | そのまま修正する（誤指摘ならはっきり却下する） |
| **確信が弱い** | 指摘は妥当だと考えるが、事実関係・影響範囲・修正方法のいずれかに不確実性が残る | **修正は進める。** そのうえで論点と判断理由を記録する |
| **判断が必要** | 設計・優先度・トレードオフの選択であり、どちらを取るかはユーザーが決めるべき | **修正しない（保留）。** 選択肢を整理する |

- 指摘を黙って落とすな。全件をこの3区分のどこかに置く
- 4. の照合で「判断が必要」に回した差分（再現できないデザイン差分、要求どうしの矛盾など）も、この3区分の「判断が必要」に合流させて同じ扱いで処理する
- 修正を入れたら検証ゲートを再実行して通す
- 修正の結果specの内容が変わるなら、specも更新して `Artifact` を再デプロイする
- 修正が要求事項・基本設計・デザインへの適合を変える内容だった場合は、4. の該当項目だけ照合をやり直す

# 7. PRを作成する

6. の修正まで終えたら、ユーザーに確認を求めずそのまま commit・push・PR作成まで進める。「判断が必要」が残っていても止まらない（下の draft の扱いに従う）。

## ブランチ

- feature branchにいる場合はそれをそのまま使う
- 2. でPRを分割した場合、2本目以降は先行PRのブランチから `git checkout -b {type}/{slug}` で切る。default branchから切らない
- default branch（main/master）にいる場合は、先に `git checkout -b {type}/{slug}` でブランチを作ってから commit する。`type` は `feat` / `fix` / `refactor` / `perf` / `style` / `docs` / `test` / `ci` / `build` / `chore` / `revert` から実装内容に合うものを選ぶ

## commit

- `git status` で未コミットの変更を確認し、`git add <ファイルパス>` で明示的に追加する。`git add .` / `git add -A` は禁止
- **`.spec/` 以下はcommitしない**（作業用ドキュメントであり、コミット対象外）
- commit messageは `<type>: <subject>` のSemantic Commit形式で、**1行のみ**。本文段落を付けない。`Co-Authored-By` などの付帯情報も付けない
- 既にcommit済みの変更がある場合、push済みのcommitを `--amend` したりforce pushしたりしない。追加のcommitとして積む

## PR

- `git push -u origin <branch>` でpushする
- 現在のブランチに既存のopen PRがあるか `gh pr view --json url,state,isDraft` で確認する
  - ある場合は新規作成せず、pushした内容がそのPRに反映されたことを確認する。実装内容がPR本文と食い違っているなら `gh pr edit` で本文を更新する
  - ない場合は `gh pr create` で作成する。2. でPRを分割した場合、2本目以降は `--base <先行PRのブランチ>` を付ける
- **「判断が必要」が1件でも残っているなら `--draft` を付けてdraft PRとして作成する。** 本文の末尾に「保留中の論点」として、6. で仕分けた「判断が必要」の各件を選択肢付きで書く。保留が0件なら通常のPRとして作成する
- タイトルは英語・70文字以内・Semantic Commit形式。本文も英語で、変更の背景（なぜ）・変更内容の要約・検証方法（実行した検証ゲート、および 4. の照合をどう行ったか）を書く。`🤖 Generated with ...` のような付帯フッタは付けない
- specの Artifact URL がある場合、リポジトリがprivateなら本文に載せる（`gh repo view --json isPrivate` で確認する。publicなら載せない）

## CI

- PR作成・push後、`gh pr checks --watch` でCIの結果を確認する
- 失敗があれば原因を調べて修正し、追加commitをpushして再度確認する。CIが通らないまま完了報告をしない
- CIの調査・修正には `check-pr` skill を使ってよい

## 分割した残りのPRがある場合

CIが通ったら、報告を待たずに 3. へ戻り、次のPRの実装に着手する。全PRについて 3.〜7. を終えるまで 8. の報告には進まない。

# 8. 報告する

## 要求事項・基本設計・デザインの充足状況

4. で作った照合表をそのまま載せる。全項目を省略せずに並べ、各項目に対応する実装の実体を示す。**「全て実装しました」という総括だけで表を省略してはならない。**

デザインの提示があった場合は、確認方法（実際に描画して確認したのか、ソースを読み比べたのか）と、残っている差分の有無を明記する。提示がなかった場合は「デザインの提示なし」と1行書く。

## レビュー指摘

3区分ごとに、以下の粒度で報告する。区分の見出しは、該当が0件でも「なし」と書いて省略しない。

- **確信が強いもの**: 修正の要約のみ。1件1行（却下した誤指摘も、却下したことと理由を1行で）
- **確信が弱いもの**: ①論点は何か ②なぜその判断をしたのか ③具体的にどういう修正をしたのか
- **判断が必要なもの**: 選択肢の一覧と、それぞれの pros/cons。選択肢の形に落とせない場合は、何が不確実なのかを整理して示す

## PR

作成（または更新）したPRのURLと、それがdraftかどうか、CIの結果を報告する。PRを分割した場合は、マージ順に全PRのURL・base branch・draftかどうか・CIの結果を並べ、3区分の報告と照合表はどのPRの内容かが分かる形で書く。

報告は、レビューの経過を追っていない人が読んで意味が通る文章にする。その場で作った用語・略称を使わず、`file:line` か実在する識別子で対象を名指しする。

「判断が必要」が1件でもあれば、**全PRを出し終えたこの時点で**判断を待つ。勝手にどちらかを選んで実装してはならない。ユーザーの判断が出たら、それを実装して該当PRのブランチにpushし、CIが通っていることを確認したうえで `gh pr ready` でdraftを解除する。分割した複数のPRに保留が残っている場合は、それぞれについて同じ処理を行う。

# 9. `.spec/goal.md` を削除する

8. の報告を出し終えたら、`.spec/goal.md` を削除する。これで Stop hook の判定が止まる。

- **削除は 8. の報告を出し終えた後に行う。** 未達のまま削除すると完了条件の確認が効かなくなる
- 「判断が必要」が残っていて判断待ちに入る場合も、そこまでが 0. で書いた完了条件なので削除する。ユーザーの判断を実装する作業は、この完了条件の対象外
