# spec-driven development 統合ワークフロー

現在の状況を自動判定し、適切なフェーズから開発を開始・継続する。

## 後から実装を指示された場合

このスキルの承認待ちに入った後で、ユーザーが `$implement` を指定するか、対象と実装内容を明示して実装・続行・完了を指示した場合は、その新しい指示を優先する。未承認の spec を理由に停止せず、`implement` スキルに処理を移して実装を続ける。すでに承認された内容について、再び承認を求めない。

この例外は、上位の指示、安全上の制約、または新しい指示の範囲を超える変更を許可しない。新しい永続化スキーマ、外部契約、認証フロー、状態の保存と管理など、新しい指示に含まれない設計判断が必要になった場合だけ、その判断をユーザーへ求める。

# 状況判定

まず次の情報を集め、現在の作業段階を判定する。

1. `git branch --show-current` で現在のブランチ名を取得
2. ブランチ名の `/` より後を slug とする（例: `feat/create-article-component` → `create-article-component`）
3. `.spec/{slug}/spec.md` の存在確認
4. specファイルが存在する場合、タスクの進捗状況を確認する（`- [x]` が完了、`- [ ]` が未完了）

> `.spec/{slug}/spec.html` が存在する場合、それは別のエージェントが HTML 形式で作成した spec である。その場合は新たに `spec.md` を作らず、**既存の `spec.html` をそのまま spec として読み・進捗もその中の `<li class="task todo">` / `<li class="task done">` を書き換えて管理する**（表示は `open .spec/{slug}/spec.html`）。以降の手順の「spec ファイル」はこの `spec.html` を指すものとして読み替える。

## フェーズ判定ルール

| 条件 | フェーズ |
|------|---------|
| main/masterブランチにいる & specなし | **Phase 1: 計画開始** |
| 作業ブランチにいる & specなし | **Phase 1: 計画開始**（ブランチは既存を使う） |
| 作業ブランチにいる & specあり & タスク未着手 | **Phase 2: 実装開始** |
| 作業ブランチにいる & specあり & タスク一部完了 | **Phase 3: 実装再開** |
| 作業ブランチにいる & specあり & タスク全完了 | **Phase 4: 仕上げ** |

判定結果をユーザーに伝えてから、該当する段階の作業を開始する。

> **⚠️ 原則: specファイルが存在しない場合、Phase 1（計画開始）以外のフェーズに進んではならない。まず spec を作成し、ユーザーの承認を得る。上記の「後から実装を指示された場合」に該当するときは、その新しい指示がこの承認待ちを置き換える。**

# Phase 1: 計画開始

ユーザーから実行したいタスクの概要を聞き、spec作成から始める。

## ブランチ準備
- タスク概要から適切なslugを考える（例：「記事コンポーネントを作成する」→ `create-article-component`）
- main/masterにいる場合：
  - リモートからプルして同期する
  - `git checkout -b {type}/{slug}` でブランチを作成する
  - `type` は `feat`, `fix`, `refactor`, `perf`, `style`, `docs`, `test`, `ci`, `build`, `chore`, `revert` から選択
- 既に作業ブランチにいる場合：そのブランチをそのまま使う

## 設計の記述基準

> テンプレートに項目を記入するだけでは不十分である。この節の基準を満たさない spec は、ユーザーに承認を求めてはならない。

spec は、別の実装者が同じ設計に基づいて実装できるように書く。次の2つを合格基準とする。

> 1. **このspecファイルだけを渡された別の人・別のエージェントが、設計上の重要な判断を自分でやり直さずに、設計の意図に沿って実装できること。**
> 2. **「基本設計」の章だけを読んだ人が、変更する対象、その構造と動作を理解できること。**

### specの章構成と、章ごとの責務

spec は次の6章で構成する。**章名も順序も変えない。**

| # | 章 | この章に書く内容 |
|---|---|---|
| 1 | 要求事項 | 何を満たせば完成なのか |
| 2 | 基本設計 | どの対象の構造と動作をどう変えるのか |
| 3 | 設計判断 | 選択肢があった箇所で、何を採用し、何を却下し、なぜそうしたのか |
| 4 | テスト計画 | 何を検証できれば、設計どおりに動いていると言えるのか |
| 5 | 詳細設計 | 2章の構造を、どの識別子・型・シグネチャ・スキーマで実現するのか |
| 6 | 実装計画 | どのファイルを、どの順で書くのか |

#### 基本設計（2章）と詳細設計（5章）の分担

2章は設計を理解するための概念と仕組み、5章はそれを実装するための確定した定義を書く。説明する対象が同じでも、目的を区別する。

| | 基本設計（2章） | 詳細設計（5章） |
| --- | --- | --- |
| 書くもの | 重要なデータ構造、概念どうしの関係、アルゴリズム、処理プロセス、状態遷移、守る条件、要求を満たす理由 | 公開シグネチャ、型・フィールド・値の定義、DBスキーマとマイグレーション、API・設定・環境変数・CLIフラグ、関数の呼び出し順、エラー型・コード |
| 詳しさ | 各概念の単位、キーと値、順序・優先順位、所有関係、処理条件を、具体例で動作を追える程度まで説明する | 実装者が識別子・型・値を決め直さずに実装できる程度まで確定する |
| 合格基準 | 5章を読まずに、主要な概念の関係と具体的な動作を説明できる | 2章で説明した設計を、確定した定義で実装できる |

データ構造の理解に必要なキー、値、順序、参照関係や、アルゴリズムの判断条件を「詳細設計だから」と省いてはならない。実装のシグネチャや全カラムの型定義は5章に書く。構造の説明に役立つ実在の識別子は2章でも使ってよいが、識別子の列挙で概念の説明を代用しない。

#### 基本設計の説明を組み立てる

**2章は、構成要素の一覧を埋める章ではない。その設計を理解するうえで最も重要な概念と、その関係・動作を読者が説明できるようにする章である。** テンプレートの見出しを順に埋める前に、関連するコードと要求を読み、次を検討する。

1. **理解の中心になる事項を選ぶ。** 要求を実現するうえで重要なのは、データ構造、アルゴリズム、処理プロセス、状態遷移、責務の分担のどれか。何を理解しないと、この設計が要求を満たす理由が分からないかを特定し、その事項と要求の対応を確かめる。「新しいコンポーネントを追加する」は答えにならない。
2. **混同されやすい概念を区別する。** 各概念が何を表し、1件が何に対応し、他の概念とどう関係するかを説明する。保存するデータと処理対象、処理の定義と1回の実行、実行権の予約と実行中の処理などを同じ語や同じ箱で表さない。具体的な入力や状態を1つ選び、どの単位で選択・更新・実行されるかを確かめる。
3. **説明の順序を選ぶ。** 読者がすでに知っている前提から、重要な概念、その関係、動作、要求を満たす理由へ進む順序を考える。冒頭に設計全体の考え方を短く書き、最も重要な説明を先に置く。データから説明する構成、処理から説明する構成などを比較し、その設計を最も少ない前提で理解できる順序を選ぶ。インフラの起動順や変更ファイルの一覧を、説明の開始点と決めつけない。
4. **必要な図を選ぶ。** どの関係や変化を図で示すと理解しやすいか、図ごとに答える問いを決める。データの形、アルゴリズムの分岐、処理順序、状態遷移、同時実行の範囲は、異なる図が必要になることがある。複数図が必要なら使う。1枚にすべてを詰め込んだり、図の数を増やすだけで説明したことにしたりしない。
5. **説明を読み直して構成を直す。** 実装の詳細を知らない読者が、本文と図だけで概念の違い、関係、具体的な動作を説明できるか確認する。分からない場合は、用語の追加だけで済ませず、説明の順序、具体例、図の役割から直す。確認の際は、各概念の関係や具体例の選択・更新・終了を本文のどこから説明できるか、実際に読み取る。「分かりやすいはず」という自己評価だけで済ませない。考察の長い経緯は spec に書かず、選んだ説明とその根拠を書く。

2章内の小見出し、順序、節の数は、設計の理解に必要な内容から決める。次の観点は**設計を検討するときの確認事項**であり、同名の節を機械的に作るための一覧ではない。関連する事項を一緒に説明してよい。該当しない項目は、末尾で簡潔に明示し、空の節を増やさない。

| 観点 | 読者が理解できるようにする内容 |
| --- | --- |
| データ構造 | 何を1件として保存・処理するか、キーと値、集合・順序・優先順位、関係と多重度、一意性、従属と寿命。概念的なデータ例を使い、保存する情報と保存しない情報を区別する |
| アルゴリズム | 入力、選択・判定条件、処理順、更新、出力、終了条件。必要な前提と守る条件を示し、具体例で処理前から処理後まで追えるようにする。性能が要件なら、何の件数に応じて処理量が増えるかと、その根拠を説明する |
| 処理プロセスと状態 | 起点、読み書きするデータ、実行する主体、順序、状態遷移、再試行と終了。同時実行時に誰が何を占有し、いつ解放するか。制限や予算がどの単位に適用されるか |
| 構成と責務 | 上記のデータと処理をどの構成要素が担当し、どの境界で情報や制御を渡すか。一覧表は関係を説明した後の補足にする |
| 変更前後と要求 | 既存のどの構造・動作をどう変え、何を維持するか。その変更によって要求を満たせる理由。未確認の性能や安全性を推測で補わない |

エージェント／LLM を使う設計では、実行単位、履歴の継承、固定手順と可変手順、前提・終了条件、プロンプトの分担、ツールの範囲と上限、モデルの割り当てを、処理の関係が分かる位置で説明する。UI を伴う設計では、利用者の目的、画面の役割と遷移、各画面の全状態、文言、既存画面から受ける制約を説明する。

#### 図と本文の対応

- 図の直前に、その図で読者が理解する関係や動作を説明する。図の後には、図から読み取るべき重要な条件や、次の説明との関係を書く。
- 箱が概念、データ1件、プロセス、実行1回のどれを表すかを明記する。矢印が参照、データの移動、呼び出し、状態遷移のどれを表すかを、ラベルや凡例で区別する。多重度、順序、所有関係、同期・非同期が理解に必要なら省かない。
- 複数図では同じ概念の名称を揃え、全体図と詳細図の対応を示す。前の図で定義していない略語や、本文と異なる単位を導入しない。
- 具体例の入力・時刻・件数・状態が、本文と図と凡例で一致しているか確認する。説明のための例を、未確認の実測値として扱わない。

新規の Markdown spec では mermaid を使う。既存の HTML spec を扱う場合は、その形式を維持し、inline SVG または HTML+CSS を使う。

#### テスト計画（4章）を詳細設計（5章）より前に置く

テスト計画は「外から観測できる振る舞い」を書く章であり、実装の形に依存しない。要求事項と基本設計から導けるものをここで先に固定する。

- 4章には「**どの振る舞い／境界条件を、どのテストで、どういう入力・状態に対して何を期待して検証するか**」を書く。正常系だけの計画は不可
- 5章「エラーハンドリング / 境界条件」を書いた結果、4章に無い境界条件・エラーケースが出てきたら、**4章に戻して追加する**。5章にだけ書いて済ませてはならない
- 期待するエラー型・コードのような確定形は5章に置き、4章からは「5章の◯◯で定義したエラー」として参照してよい

### 承認を求めてはならない記述

次の記述は、設計が未完成だと判断する。該当する記述が残っている spec は、ユーザーに承認を求めてはならない。

- 「〜する」「〜を追加する」「〜を適切に処理する」で止まっている（処理内容や実現方法を説明していない）
- 「◯◯系のモジュール/tool/toolset を追加する」のように、**追加する対象の名前・構造・登録方法が書かれていない**
- 「終了アクション（finalize **等**）を導入」のように、**名前を "等" / "など" で曖昧にしている**、または enum 値・フィールド・型が確定していない
- 「実装時に確定する」「あとで決める」「必要に応じて」で **判断を先送りしている**
- 既存コードの変更を「〜を変更する」とだけ書き、**変更前（現状の実在シグネチャ）と変更後の具体形が対比されていない**
- 2章が構成要素・変更ファイル・型・スキーマの一覧になり、重要な概念の関係と動作を読者に推測させている
- 図があっても、データの形、選択・更新の条件、実行や状態の単位が分からない。本文と図と凡例が異なる内容を示している

こうした記述では、実装者が設計上の判断をやり直す必要がある。**ファイル名や既存の識別子を正しく引用していても、判断が未確定なら設計は未完成である。** 表、箇条書き、実在するパスの有無だけで、設計が具体的に書かれていると判断しない。

### 具体的な記述の例

以下は説明する内容の例であり、小見出しや順序をそのまま採用するためのテンプレートではない。

次の例は、各項目に必要な詳しさを示している。不十分な例（❌）に当てはまる記述は、具体的な例（✅）と同程度まで書き直してから提出する。

- **基本設計 / 説明の構成**
  - ❌ 「構成要素と責務の表 → 全体の接続図 → テーブルの一覧」。各要素は説明していても、読者が何を単位として扱い、どう次の処理を選ぶかを組み立て直す必要がある。
  - ✅ 定期処理の設計なら、まず「次に処理する対象を選ぶデータ」と「実際に実行する仕事」が同じか異なるかを説明する。次に、キーと時刻の具体例から対象の選択と更新を追う。同時実行が重要なら、実行の単位と予約・解放の関係を別の図で示す。構成と責務の表は、その仕組みをどの要素が担当するかを確認する補足にする。この順序を他の設計にも一律に適用せず、その設計で重要な概念から組み立てる。
- **基本設計 / データモデルの変更**
  - ❌ 「計画テーブルと変更項目テーブルを追加する」
  - ✅ 「エンティティが2つ増える。**計画** ―― 1回の相談のまとまり。テナントに従属し、対象の絞り込み条件と状態を持つ。**変更項目** ―― 計画に従属する1件の変更案で、既存のルールを0〜1件参照する（新規追加の項目はどのルールも参照しない）。計画1件に対し変更項目は0〜N件、計画が破棄されると変更項目も消える。一意性は計画がID単体、変更項目は計画IDとの複合。**既存のルールのモデルは変更しない** ―― 適用時に新しい版を作るだけで、参照は変更項目からルールへの片方向」
- **基本設計 / 状態の保存と管理**
  - ❌ 「計画の状態をDBに保持する」
  - ✅ 「計画は永続化され、`open` → `applied` / `discarded` の3状態を取る。状態を書き換えるのは適用処理と破棄処理の2経路のみで、エージェントは変更項目の追加しか行わない。エージェントの会話は計画より長く保たれる必要があるため、保持期間は計画の最終操作からではなく**最初の操作から**数える。会話の履歴を失った場合に備えて、現状を読み直すツールを1つ用意する」
- **基本設計 / エージェントのワークフロー**
  - ❌ 「エージェントが指示を受けて変更案を出す」
  - ✅ 「1つの指示が1回の実行に対応し、次の指示では、前回の会話を引き継いで新たに実行する（実行の上限とキャンセルを指示ごとに管理する）。手順は『現状把握 → 意図の分解 → 対象の確定 → 根拠の収集 → 提案 → 返答』の6手順を固定し、指示によって変わるのは4番目の手順で何を読むかだけ。3〜5番目の手順は意図の数だけ繰り返す。待機状態は設けない。質問が必要な場合は返答に書き、その実行を終了する」
- **基本設計 / 画面**
  - ❌ 「一覧画面と詳細画面を追加する」
  - ✅ 「画面は3つ。一覧画面には計画を表示し、状態で絞り込めるようにする。作成画面では対象を絞り込み、最初の指示を入力する。詳細画面には変更項目の一覧と指示の入力欄を表示する。詳細画面が取りうる状態は7つ：初期（項目0件）／エージェント実行中／項目あり・未適用／適用中／適用済み／適用の一部失敗／破棄済み。**各状態の画面をすべて示す。** 実行中は入力欄を無効化し、進行の表示は『何をしているか』を文言で示す」
- **詳細設計 / 公開シグネチャ**
  - ❌ 「close 用の tool を sub-agent に配線する」
  - ✅ 「`agent/toolset.go` の `ToolSetResolver` が現在対応する ID は `core_ro` / `slack_ro` のみである（`toolset.go:NN`）。ここに ID `case_writer` を追加し、`case__update_case_status(ctx context.Context, caseID string, status CaseStatus) error` を含む `gollem.ToolSet` を返す。`threadcase.buildToolResolver` は `OmitCore: true` を保ったまま、返す集合に `case_writer` を追加する」
- **詳細設計 / データモデル・型定義・enum**
  - ❌ 「終了アクションを追加する」
  - ✅ 「`ReplanResult`（`plan.go:NN`）に `Action ReplanAction` を追加。`ReplanAction` は `string` enum で `"investigate" | "question" | "finalize"` の3値。既存の『Tasks も Question も空なら終了』分岐（`plan.go:70`）を削除し、`Action == "finalize"` のときだけ実行ループを終了する。`Validate()` はこの3値以外の値や空文字を拒否する」
- **詳細設計 / 処理シーケンス**
  - ❌ 「調査結果を受けて host が materialize する」
  - ✅ 「① `Run[MaterializeResult](ctx, runner, req)` が検証済み `*MaterializeResult{Title string; Description string; Fields map[string]string}` を返す → ② `threadcase.handleMention` がそれを受け `caseRepo.UpdateCase(ctx, caseID, result.Title, result.Description, result.Fields)` を呼ぶ。close 処理はサブエージェントによるツール呼び出しの中で完了するため、この処理の流れには含まれない」
- **詳細設計 / 分岐・境界・エラー**
  - ❌ 「失敗は適切に伝播する」
  - ✅ 「サブエージェントで panic が発生した場合は、`executePhase` で recover する。(1) `results[i] = TaskResult{State: Failed, Error: err}` として失敗を記録し、planner に渡す。(2) `errutil.Handle(ctx, err)` で Sentry に送信する。実行予算を使い切った場合は、最後の失敗を `FallbackReason` に格納して返す」

（上の識別子・行番号は書き方の見本。実際には**あなたが読んだ実コードの実名**に置き換えること。）

### 各セクションが必ず満たす条件

**基本設計（2章）**
- 上の「基本設計の説明を組み立てる」と「図と本文の対応」に従う。最も重要な概念の関係と動作を説明し、観点の一覧を固定の小見出しに置き換えない。
- データの単位・関係・寿命、処理条件・更新・終了、変更前後と維持する動作を確認する。エージェントやUIを伴う場合は、それぞれに必要な事項も説明する。

**設計判断（3章）**
- 選択肢が複数あった箇所（状態の保存と管理・同期/非同期・保存先・型の受け渡し方・認証フロー・待機状態を持つか等）は **採用案・却下案・採用理由** を残す（`AGENTS.md`「Design Fidelity」対応）

**テスト計画（4章）**
- 「どの振る舞い／境界条件を、どのテストで、どういう入力・状態に対して何を期待して検証するか」まで。正常系だけは不可

**詳細設計（5章）**
- **公開シグネチャ**: 新規／変更する関数・メソッド・型の **実際のシグネチャ（引数名・型・戻り値・エラー型）**。既存を変更するなら **現状（実在の識別子・行）→ 変更後** を対比する
- **データモデル / 型定義**: **フィールド名・型・意味・制約（必須/任意・値域）** まで。enum は値を確定させる
- **永続化スキーマの変更（DBスキーマ / repository インターフェース / 永続化フォーマット）**: 変更の有無を**必ず判定して明示する**。変更があるなら、テーブル・カラム名／型／NULL可否／デフォルト値／インデックス／制約と repository のメソッドシグネチャを **現状 → 変更後** で対比し、マイグレーション手順・既存データの扱い・後方互換性・ロールバック可否まで書く。変更がないなら「なし」と明記する
- **処理シーケンス**: 主要ユースケースごとに **関数の呼び出し順序** と **各ステップの入出力** が追える形で（2章の流れを、実在の関数名で具体化したもの）
- **分岐・境界条件・エラーケース**: 正常系だけでなく異常系・境界値・並行時の振る舞いを列挙し、**返すエラー型/コード** まで書く。ここで出た項目は4章に反映済みであること

### 設計判断の先送り禁止

「あとで決める」「実装時に判断」「必要に応じて」で設計判断を残すことを**禁止する**。設計上の分岐（状態の保存と管理・同期/非同期・保存先・型の受け渡し方・命名・enum 値）は spec の中で**確定させる**。

情報が足りず決められない項目は、`decision-brief` スキルで選択肢と根拠を示して判断を求める。spec には未決の項目を「要判断」として記録し、下書きとしてレビューに提示してよい。ただし、未決の項目を確定済みとして承認や実装を進めてはならない。回答を受けたら本文と設計判断を更新する。

ユーザーに問う箇所は、会話で尋ねるだけでなく **spec 本文の該当位置に `> ⚠️ **要判断**: ...` の引用ブロックを置いて強調表示する**（書式は「統合specファイルの作成」を参照）。会話だけで問うと、spec を後から読む人にはどこが未確定なのか分からない。

### 省略できる記述

目的は「**実装者が判断を迫られる箇所を、あらかじめ決めておくこと**」。実装コードの全文や、getter・ボイラープレートの列挙は不要。省いてよいのは「**設計が確定していれば機械的に書けるだけのコード本体**」に限る。

⚠️ 「自明だから省く」と判断する場合は、次の条件を厳密に確認する。ある識別子の**名前・型・シグネチャ・enum 値・呼び出し順**が spec から一意に読み取れないなら、それは "自明" ではなく **"未確定"** である。未確定の事項を「自明」として省略してはならない。

2章では概念と動作を理解できるように説明し、5章では対応する実装上の定義を確定する。同じデータや処理を両章で扱ってよいが、同じ説明を繰り返さない。

### 既存コードに基づく記述

既存コードに触れる設計は、`AGENTS.md`「Grounding & Judgment」に従い **実際のコード・スキーマを読んでから** 書く。既存の型・関数・パスに接続する箇所は、**実在する名前で参照する**。まだ読んでいない箇所を「たぶんこうなっている」で書くことは、Honesty Over Plausibility 違反である。

### 承認前の確認（必須）

spec をユーザーに提示する **前に**、次を1項目ずつ点検する。満たしていない項目があれば修正する。この確認を終えるまで、ユーザーに提示してはならない。追加のモデルやサブエージェントを呼ばず、現在の作業内で本文と図を読み直す。

**基本設計（2章）**
- [ ] **この設計で最も重要なデータ構造・アルゴリズム・処理プロセスを選び、それを中心に説明しているか。** 固定の項目一覧や構成要素の表を埋めるだけになっていないか
- [ ] 冒頭から、設計全体の考え方と要求を満たす理由が分かるか。読み手が理解すべき前提を、使う前に説明しているか
- [ ] 各概念の意味と1件の単位、キーと値、関係、多重度、一意性、寿命を説明しているか。異なる概念を同じ語や箱で表していないか
- [ ] 具体的な入力や状態から、選択・判定・更新・実行・終了を追えるか。処理前後のデータと、守る条件を示しているか
- [ ] 同時実行や再試行が関係する場合、占有・解放、重複時の動作、制限や予算を適用する単位が分かるか
- [ ] 必要な関係を図で示しているか。複数図が必要な説明を1枚に詰め込んだり、図の追加だけで説明したことにしたりしていないか
- [ ] 箱・矢印・多重度・凡例の意味、本文と図の用語・単位・例の値が一致しているか。図どうしの関係が分かるか
- [ ] 5章を読まずに、読者が主要な概念の関係と具体的な動作を説明できるか。不足があれば説明の順序や図から直したか
- [ ] 変更前後と維持する動作、エージェントやUIに関係する事項を、設計に適した位置で説明しているか
- [ ] 概念の理解に必要な情報と、5章で確定する実装上の定義を区別しているか

**詳細設計（5章）**
- [ ] 新規／変更する関数・メソッド・型に、**実際のシグネチャ**（引数名・型・戻り値・エラー型）が書かれているか
- [ ] 既存コードを変更する箇所は、**変更前の現状**（実在の識別子・行）と**変更後**が対比されているか
- [ ] 主要データ構造に、**フィールド名・型・意味・制約**が書かれているか
- [ ] 主要ユースケースが、**関数の呼び出し順と各ステップの入出力**で追えるか
- [ ] enum / 定数 / 識別子の **値が確定** しているか（"等" / "など" で曖昧にしていないか）
- [ ] **永続化スキーマ（DBスキーマ・repository インターフェース・永続化フォーマット）の変更有無を明示したか。** 変更があるなら現状 → 変更後の対比・マイグレーション手順・既存データの扱い・後方互換性・ロールバック可否まで書けているか。変更がないなら「なし」と書いてあるか
- [ ] 既存コードに接続する名前が、推測でなく **実在を確認済み** か

**全体**
- [ ] ユーザーの判断が必要な箇所が `> ⚠️ **要判断**: ...` の引用ブロックで表記され、**決めること・選択肢・各選択肢を採用した場合に起きること・現時点の推奨**が書かれているか。判断が必要な箇所がないなら、このブロックが1つも残っていないか
- [ ] 3章に、選択肢のあった箇所の **採用案・却下案・採用理由** が書かれているか
- [ ] 4章が、5章「エラーハンドリング / 境界条件」で列挙した項目を**すべて含んでいる**か
- [ ] 「実装時に確定」「あとで決める」「必要に応じて」等の **先送り表現が残っていないか**

## 統合specファイルの作成

specは **Markdown** で作成し、`mo` コマンドでブラウザに表示してレビューに供する。

- `.spec/{slug}/` ディレクトリを作成
- specの実体は **`.spec/{slug}/spec.md`** に配置する
- 本文は日本語で記述する
- **図は mermaid のコードブロックで表現してよい**（`mo` は mermaid を描画できる）。ASCII Art は使わない
- **進捗チェックボックスは GitHub 互換の `- [ ]`（未完了） / `- [x]`（完了）で表現する。** 実装時はこの `[ ]` ↔ `[x]` を書き換えて進捗を管理する（grepしやすく編集も容易）
- **ユーザーの判断が必要な箇所は `> ⚠️ **要判断**: ...` で始まる引用ブロックで表記する。** 引用ブロックと `⚠️` により、本文の地の文から区別できる状態にする。書く場所は判断が関わる章の該当位置（例: 保存先の選択なら「2. 基本設計 → 状態の保存と管理」の直後）で、章末や文書末にまとめない。ブロックの中には **①決める事項 ②名前を付けた選択肢 ③各案を採用した場合に起きること ④現時点での推奨案と理由** を書く。ユーザーの判断が出たらこのブロックを削除し、確定した内容を本文と「3. 設計判断」へ反映する

以下のテンプレートを `.spec/{slug}/spec.md` の出発点とする（`{タスク名}` 等のプレースホルダは埋める）:

````markdown
# {タスク名} Specification

## 1. 要求事項 (Requirements)

### 概要
[タスクの概要と目的]

### 機能要件
- [要件1]
- [要件2]

### 非機能要件
- [パフォーマンス要件]
- [セキュリティ要件]

### 制約事項
- [技術的制約]
- [ビジネス制約]

## 2. 基本設計 (High-Level Design)

> この章だけで、主要な概念の関係、具体的な動作、要求を満たす理由が理解できるようにする。小見出しと順序は、その設計で最も重要なデータ構造・アルゴリズム・処理プロセスから決める。以下は構成の出発点であり、固定の項目一覧ではない。

### 設計全体の考え方
[何をどの単位で扱い、どの関係と処理によって要求を実現するか。主要な概念を定義し、変更前後と維持する動作を短く説明する]

### [最も重要なデータ構造・アルゴリズム・処理プロセスの具体的な見出し]
[この概念が必要な理由、何を1件として扱うか、他の概念との関係、重要な条件を説明する。実装の構成要素や変更ファイルの一覧で代用しない]

[この図で理解する関係や動作を、図を読む前に説明する。mermaid の図を作り、箱・矢印・単位・凡例の意味を明記する]

[図から分かる条件と、次の説明につながる関係を説明する]

### [具体例を使って関係や動作を追う見出し]
[入力と処理前のデータ・状態を示す。どの対象がどの条件で選択され、どのデータが更新され、どの処理が実行・終了するかを追う。処理後の状態と守られる条件を示す]

[必要なら、データの変化、処理順序、状態遷移などを別の mermaid 図で説明する。前の図と同じ概念を同じ名称で示し、この図が答える問いを明記する]

> 必要に応じて節と図を追加し、不要な例や図は削除する。データの形、アルゴリズム、処理順序、状態遷移、同時実行の範囲を、理解しやすい順序で説明する。構成と責務の表は補足として使う。エージェントやUIの要件も関係する節に含め、該当しない事項は末尾で簡潔に明示する。

## 3. 設計判断 (Design Decisions)

> 選択肢が複数あった箇所（状態の保存と管理・同期/非同期・保存先・型の受け渡し方・認証フロー・待機状態を持つか等）を、実装者が同じ判断を繰り返さずに済むように記録する。なければ「比較が必要な選択肢なし」と明示。

- **[論点]** — 採用: [採用案] / 却下: [却下案] / 理由: [採用した理由]

> ⚠️ **要判断**: [決めること]
>
> - **案A: [名前]** — [内容]。採用した場合: [結果]
> - **案B: [名前]** — [内容]。採用した場合: [結果]
>
> 推奨: [どちらを推すか] — [理由]

> この「要判断」ブロックは、ユーザーの判断が必要な箇所に置く。配置する場所は、判断に関わる章の該当位置であり、この3章に限らない。判断が確定したらブロックを削除し、確定内容を本文と上の設計判断リストへ反映する。判断が必要な箇所がなければブロックごと削除する。

## 4. テスト計画 (Test Plan)

> 外から観測できる振る舞いを書く章。「どの振る舞い/境界条件を、どのテストで、どういう入力・状態に対して何を期待して検証するか」まで具体的に書く。正常系だけのテスト計画は不可。「5. 詳細設計」の境界条件を書いた結果ここに無いケースが出たら、この章に戻して追加する。

- [ ] 正常系ユニットテスト（対象 → 入力/状態 → 期待する結果）
- [ ] 境界値・異常系ユニットテスト（ケース → 入力/状態 → 期待するエラー型/コード・戻り値）
- [ ] 統合テスト（対象の経路 → 入力/状態 → 期待する結果）

## 5. 詳細設計 (Detailed Design)

> 「2. 基本設計」の構造を、実装に必要な名前・型・値を確定した形で書く章。合格基準は「この章だけを渡された実装者が、識別子・型・値を自分で決め直さずに書けること」。該当がない項目は「なし」と明示する。

### 公開シグネチャ
[新規/変更する関数・メソッド・型の実際のシグネチャ。引数名・型・戻り値・エラー型まで。既存を変更するなら *現状のシグネチャ（実在の識別子・行）→ 変更後のシグネチャ* を併記。例: `func (s *Service) Foo(ctx context.Context, id ID) (*Result, error)`]

### データモデル / 型定義
[「2. 基本設計」で説明したデータ構造やエンティティを、フィールド名・型・意味・制約（必須/任意・値域）まで具体的に書く。enum は値を確定させる。エンティティに現れない補助的な型もここに書く]

### データスキーマ / マイグレーション

> **変更がある場合は必ず明示。変更がないと判断した場合も「なし」と明記する。**

- **DBスキーマ**: 追加・変更・削除するテーブル／カラムを、名前・型・NULL可否・デフォルト値・インデックス・制約（PK/FK/UNIQUE）まで *現状 → 変更後* で対比
- **repository インターフェース**: 永続化層のメソッドシグネチャの追加・変更・削除を *現状 → 変更後* で対比
- **マイグレーション**: 適用手順、既存データの扱い（バックフィル／変換／削除）、後方互換性（旧コードは新スキーマを読めるか・その逆はどうか）、ロールバック可否と失敗時の復旧手段
- **その他の永続化フォーマット**: メッセージフォーマット、ファイル・オブジェクトストレージの保存形式、キャッシュのキー設計など

### 外的インターフェース (External Interfaces)

> 外部から観測・利用される境界は、後から変更すると影響範囲が大きいため、設計段階で具体的に確定させる。以下のうち該当するものはすべて、名前・型・デフォルト値・必須/任意・後方互換性への影響まで明記する。該当がない項目は「なし」と明示する。

- **API / エンドポイント**: 追加・変更するエンドポイント、リクエスト/レスポンスのスキーマ、ステータスコード、認証方式
- **設定 (Configuration)**: 追加・変更する設定項目、設定ファイルのキー、デフォルト値、許容値の範囲
- **環境変数 (Environment Variables)**: 追加・変更・削除する環境変数名、用途、デフォルト値、必須かどうか
- **CLIフラグ・引数**: 追加・変更するコマンドラインフラグ、引数、サブコマンド
- **外部連携 / 権限**: 外部サービス連携、必要なOAuthスコープ・IAM権限、Webhook など

### 処理シーケンス
[「2. 基本設計」の主要ユースケースの流れを、実在の関数・メソッド名で具体化したもの。呼び出し順序と各ステップの入出力が追える形で。必要なら sequence 図（mermaid）]

### エラーハンドリング / 境界条件
[「どういう入力/状態のときに何が起きるか」を具体的に列挙。異常系・境界値・並行時の振る舞い、返すエラー型/コードまで。**ここで列挙した項目は「4. テスト計画」に反映済みであること**]

### UI / その他のインターフェース
[コンポーネント構成、状態管理の実体、上記に当てはまらないインターフェース仕様。「2. 基本設計」の画面要件を実装に必要な内容まで具体化したもの]

## 6. 実装計画 (Implementation Plan)

### 影響を受けるファイル
新規作成:
- [ ] `path/to/new-file1.ext`
- [ ] `path/to/new-file2.ext`

修正:
- [ ] `path/to/existing-file1.ext`

削除:
- [ ] `path/to/delete-file.ext`

### 実装ステップ

> PRを分割する場合は、PRごとに小見出しを立て、含める変更と依存する先行PRを書く。

- [ ] **Step 1**: [ステップの説明]（詳細な作業内容 / 影響するファイル）
- [ ] **Step 2**: [ステップの説明]（詳細な作業内容 / 影響するファイル）
- [ ] **Step 3**: [ステップの説明]（詳細な作業内容 / 影響するファイル）

### リリース準備
- [ ] ドキュメントの更新（特に「外的インターフェース」の変更点 — API・設定・環境変数など — を反映する）
- [ ] マイグレーション（必要な場合）
````

## spec作成後の必須手順

> **次の手順を番号順に実行する。省略してはならない。**

0. **確認（必須）**: ブラウザに表示する前に、上の「設計の記述基準 → 承認前の確認（必須）」チェックリストを1項目ずつ確認する。1つでも未達があれば **表示・レビュー依頼に進まず、spec を直してから** 次へ進む。特に「2章だけで変更する対象、その構造と動作を理解できるか」と、「承認を求めてはならない記述」の各項目（"等"で曖昧にする表現・判断の先送り・変更前後の対比やシグネチャの不足）が残っていないかを最後に見る。
1. **ブラウザに表示する（必須）**: `mo .spec/{slug}/spec.md` を実行してブラウザに表示する。`mo` はファイルを監視して再表示するため、spec を修正しても再実行は不要（必要に応じてユーザーに再読み込みを促す）。
2. **ユーザーにレビューを依頼し、ここで停止する（必須）**: specを提示した状態でレビューを依頼し、ユーザーから明示的な承認を得るまで Phase 2 に進まない。「要判断」ブロックが残っている場合は、レビュー依頼の文でも**どの章のどの点について判断が必要かを一覧で示す**（spec 本文のブロックと重複してよい）。ただし、その後に `$implement` または対象と実装内容を明示した実装・続行・完了の指示を受けた場合は、その指示を承認として扱い、停止せず実装へ進む。

# Phase 2: 実装開始

specファイルに基づいて実装を開始する。

## コンテキストの整理
- **コンテキストが実際に逼迫している場合に限り**、実装開始前に `/compact` を実行して圧縮する。Phase 1での議論やspec作成過程の詳細はspecファイルに集約されているため、圧縮しても実装に必要な情報は失われない
- 逼迫していないなら圧縮しない。Phase 1 の議論には spec に書き切れなかった文脈（却下案についての評価やユーザーの意図）が残っており、実装中の判断に役立つ。余裕がある段階で圧縮すると、その情報を失う

## specの読み込み
- ファイルパスが引数で与えられた場合はそのパス、なければブランチ名のslugから `.spec/{slug}/spec.md` をspecとして読み込む
- specの全6章（要求事項・基本設計・設計判断・テスト計画・詳細設計・実装計画）を把握してから実装に着手する。**基本設計で全体の構造と動作を理解してから詳細設計を読む**

## 調査・リサーチ
- 実装中にライブラリのAPIやフレームワークの仕様を確認する必要がある場合、Web検索が有効なら公式ドキュメントを参照する
- 不明な仕様や使い方があれば、推測で実装せず調べてから進める。Web検索が使えず確認できない場合は、推測で書かずユーザーに確認する

## 実装の進め方
- 実装計画のステップに沿って順に進める
- 完了した作業や編集が終わったファイルは、対応するチェックボックス（`- [ ]` → `- [x]`）を書き換えて進捗を記録しながら進める（最後にまとめてではなく、都度実施）
- 進捗を更新すると同時にspecの内容を見直し、実装すべき内容や方向性を確認する
- spec を書き換えても `mo` がファイルを監視・自動更新するため、再実行は不要
- 実装中に追加の指示があった場合は specファイル（`spec.md`）も更新する
- **spec に書かれていない永続化スキーマの変更（DBスキーマ・repository インターフェース・永続化フォーマット）が必要になったら、黙って実装せず、その場でユーザーに変更内容（現状 → 変更後・既存データへの影響）を伝えて判断を求める。** 合意が取れたら spec の「5. 詳細設計 → データスキーマ / マイグレーション」に反映してから実装する
- **基本設計に書かれた構造（状態の保存と管理・責務境界・エージェントの手順や上限・画面の状態）を変える必要が出た場合も、黙って変更せずユーザーに判断を求める。** 合意が取れたら「2. 基本設計」と、必要なら「3. 設計判断」に反映してから実装する
- 実装に支障をきたす問題が発生しない限り、最後まで作業を続け、完了させる
- `// TODO` や `// FIXME`、仮実装、スタブなどを残さない。すべての機能を完全に実装し切ること

## git add
- ファイルを変更・作成したらその都度 `git add` する。実装完了時にまとめてではなく、変更のたびに実施する
- **`git add .` や `git add -A` のような一括追加は禁止。** 必ず `git add <ファイルパス>` で対象ファイルを明示的に指定すること
- **specファイル（`.spec/` 以下）は `git add` しない。** specはあくまで作業用ドキュメントであり、コミット対象に含めない

# Phase 3: 実装再開

途中まで進んでいる実装を継続する。

- specファイル（`spec.md`）を読み込み、チェックボックスの状態（`- [ ]` / `- [x]`）から進捗を把握する
- 未完了のステップの最初から実装を再開する
- Phase 2と同じルールに従って進める

---

# Phase 4: 仕上げ

実装計画のタスク（`- [ ]` / `- [x]`）がすべて完了になっている状態。

- specを最終確認し、漏れがないか点検する
- 「4. テスト計画」に基づいてテストが通ることを確認する
- ユーザーに完了報告する
