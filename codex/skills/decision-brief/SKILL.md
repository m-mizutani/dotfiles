# 判断資料

`AGENTS.md` の User Decisions に従い、ユーザーに判断を求める前に使う。アーキテクチャ、データモデル、外部契約、セキュリティ、永続化に関する選択だけでなく、小さく容易に変更できる選択も対象とする。自分で決める権限がある事項は、ユーザーに選ばせない。資料の長さは判断に必要な内容に合わせる。

## 読者の理解を最優先にする

**最優先課題は、読者が判断に必要なメンタルモデルを形成することである。** この開発の実装を知らない読者が、重要な概念の意味と関係、現在の動作（as-is）、目指す動作（to-be）、各案で変わる部分を説明できる状態にする。文字や項目を並べただけでは説明したことにならない。比較表や選択肢は、この理解を形成してから示す。

本文やテンプレートの項目を埋める前に、関連する実装と要求を読み、次を検討する。

1. **理解に必要な概念を選ぶ。** 読者は何を理解すれば各案の違いを判断できるか。データの単位、処理、状態、責務のうち、この判断を左右するものを特定する。各概念が何を表し、1件が何に対応し、他とどう関係するかを確かめる。識別子や構成要素の一覧で代用しない。
2. **現在と目標を同じ具体例で確かめる。** 誰が何をしたとき、現在は何が起き、変更後は何ができるようになるのか。入力、対象、処理、結果を揃えて説明する。共通の目標と、各案で異なる実現方法を区別し、未採用の案を決定済みの構造として描かない。
3. **原則として図で関係と変化を説明する。** データ構造、処理順序、状態遷移、責務、保存と参照など、理解に必要な関係を描く。図ごとに読者が答えられる問いを決める。現在と目標を同じ名称・単位・対応する配置で示し、維持する部分と変える部分を明示する。複数の図が必要なら使い、1枚にすべてを詰め込まない。関係や動作の変化がなく、値だけの比較を表で十分に示せる場合に限り図を省いてよい。
4. **読者が理解できる順序を選ぶ。** 冒頭は、対象の役割と今回実現したい結果を短く示す。その後に重要な概念と図、現在と目標の違いを説明し、その理解に基づいて決める事項を示す。未説明の識別子、保存先の列挙、変更ファイル、作業上の都合から始めない。小見出しは案件の内容から決め、確認項目をそのまま固定の節にしない。
5. **制約を関係する箇所で説明する。** 制約は、どのデータ、処理、関係、または案の結果を制限するかと一緒に説明する。冒頭に制約の一覧を置いても理解の代わりにはならない。「単純な解決方法がない理由」は冒頭の必須項目にせず、判断に影響する場合だけ各案の比較や補足に置く。

Markdown の図は Mermaid を使う。図の直前に何を見るかを説明し、直後に重要な条件と判断事項との関係を書く。箱が概念、データ1件、処理、実行1回のどれか、矢印が参照、呼び出し、データの移動、状態遷移のどれかをラベルや凡例で示す。理解に必要な多重度、順序、所有関係、同期・非同期を省かない。本文・図・具体例の用語と値を一致させ、確認済みの動作と提案を区別する。

## 資料の作成と提示

関連する実装と公式仕様を確認してから、`.spec/{branch-slug}/decision-{topic}.md` に資料を作る。ブランチ名から slug を取得できない場合は `.spec/decisions/decision-{topic}.md` に作る。読者の理解順に、次を含める。これは必要な内容の確認事項であり、固定の章構成ではない。

- 対象の役割と目的、重要な概念とその関係を示す図、同じ具体例による現在と目標の動作。固有の用語は最初に使う箇所で意味を説明する
- この理解に基づいて決める事項と、未決のまま進められない作業
- 各案を共通の項目で比較する表。通常は3〜5項目とし、小さな判断では結果が異なる項目だけにする
- 各案で変更する箇所、利用者から見た変更前後の動作、後から変更する費用
- 「あるべき姿」と「現実解」の2つの基準で選んだ案。「あるべき姿」は、既存実装に制約されず、長期的な保守性、モデルの整合性、抽象化の適切さを重視して選ぶ。「現実解」は、実装費用、互換性を損なう変更の回避、保守性を考慮して選ぶ。それぞれに採用理由と不利な点を添える。異なる案を選んだ場合は、現実解とあるべき姿の違い、後からあるべき姿へ変更するために必要な作業を書く
- 確認済み・未確認の前提

提示前に、本文と図だけから、読者が重要な概念の違い、現在の動作、目指す動作、各案で変わる部分を説明できるか読み直す。具体例の入力から結果までを本文と図で追い、制約がどこに作用するか確認する。説明できなければ、文章を足すだけで済ませず、概念の選び方、図、説明順を直す。

作成後は `mo <資料のパス>` で表示する。Claude Code の Artifact は使わず、ページ上での選択も待たない。会話でユーザーが答えた内容を決定として扱い、必要があれば資料にも決定内容を追記する。
