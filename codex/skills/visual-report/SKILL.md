# 図を中心にした報告資料

報告を求められた事項を、対象について予備知識がない読み手でも上から読むだけで理解できる資料にまとめる。会話の経緯を知っていることを前提にしない。

1. 報告の主題、読み手が読んだ後に分かること、読み手に求める行動を1文ずつ決める
2. 主張ごとに根拠（ファイルと行、コマンドの出力、ログ、URL）を確認し、確認済みの事実、推測、未確認の事項を区別する
3. 結論の理解に必要な概念を3〜7個選び、最初に使う箇所で「何を表すか」「1件が何に対応するか」を定義する
4. 本文を書く前に図の一覧を決める。各図には、その図を見た読み手が答えられる問いを1つ決める。全体像の図を含め3枚以上を基本とし、各節に主張を示す図を1枚置く。構成は構成図、順序はシーケンス図、状態は状態遷移図、時刻はタイムライン、原因は因果の連鎖、変更前後は同じ配置の2枚の図で示す。図には凡例を付ける
5. 1つの具体例を資料全体で使い、図と本文で同じ名前を使う。経緯を時系列で並べない

6. 情報を「必ず伝える情報」（読まないと結論、現在の状態、求められている行動を誤解する情報）と「補足の情報」（詳しい手順、ログの抜粋、計測条件、採らなかった案、根拠の一覧）に分ける。必ず伝える情報は常に表示する。補足の情報は `<details><summary>中身が分かる名詞句</summary>...</details>` に折りたたみ、読み手が気になった点だけを開けるようにする。強調は各節で最初に読むべき1文だけに使う

資料は「結論 → 全体像 → 重要な概念 → 本題 → 現在の状態と残っている課題 → 確認できていない事項 → 根拠」の順にする。本題の節は主題に合わせて分ける。

`tmp/report-{slug}.md` を作成する。図は mo が描画できる mermaid で描く。作成後は `mo <資料のパス>` で表示する。Claude Code の Artifact は使わない。会話には結論、読み手に求める行動、確認できていない事項、資料のパスを書き、資料の本文を転載しない。
