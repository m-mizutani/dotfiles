# 判断資料

複数案があり、アーキテクチャ、データモデル、外部契約、セキュリティ、永続化に関する判断をユーザーへ依頼するときに使う。違いを一文で説明でき、容易に戻せる選択には使わない。

関連する実装と公式仕様を確認してから、`.spec/{branch-slug}/decision-{topic}.md` に資料を作る。branch slug を得られない場合は `.spec/decisions/decision-{topic}.md` に作る。資料には次を含める。

- 決める事項と、未決のまま進められない理由
- 冒頭の課題説明。対象が何をするものか、現在の構造と動作、衝突している要求と制約、単純な解が無い理由、資料内で使うリポジトリ固有の語の意味。この案件の全容と実装の詳細を知らない読者が、これだけで課題を理解できる粒度で書く
- 3〜5個の比較軸を揃えた選択肢の表
- 各案の具体的な変更、利用者から見た before/after、後から変更する費用
- 2つの基準それぞれの最適案。「あるべき姿」は長期的な保守性・モデルの整合性・抽象化の適切さから既存実装を前提にせず選び、「現実解」は実装コスト・破壊的変更の回避と保守性の均衡から選ぶ。各案にその基準で選ぶ理由と引き受ける不利を添え、2つが分かれる場合は現実解に残る差と後からあるべき姿へ移すために必要になることを書く
- 確認済み・未確認の前提

作成後は `mo <資料のパス>` で表示する。Claude Code の Artifact は使わず、ページ上の選択も待たない。ユーザーの会話上の回答を決定として扱い、資料を更新する必要があれば決定内容を追記する。
