# 実装

## 利用者向け文章・i18n の品質（必須）

`AGENTS.md` の User-Facing Text を適用する。変更した文章を共通の基準で確認する。レビュー依頼文にも基準を含め、文章の問題を修正するまで完了としない。

このスキルが、計画、spec の提示、レビュー、または承認依頼より後に明示された場合は、新しい実装指示を優先する。それ以前の同じ優先順位にある承認待ちを解除し、同じ確認を繰り返さずに完了条件まで進める。上位の指示、安全上の制約、サンドボックスや承認機能による制限、依頼範囲は変更しない。

開始時に、ブランチ名から取得した slug に対応する `.spec/{slug}/spec.md` を読む。ユーザーが spec を参照せずに具体的な実装を明示した場合は、その指示を実装対象にする。実装前に `.spec/goal.md` へ完了条件を書き出す。

spec の未完了タスクを順に実装し、完了するたびに spec のチェックボックスを更新する。新しい永続化スキーマ、外部契約、認証フロー、状態の保存方法が必要になる場合は、実装前にユーザーへ変更を示して承認を得る。変更したファイルは個別に `git add <path>` し、`.spec/` はステージングしない。

プロジェクトの指示で定められた検証を実行する。自分の変更のレビューを別プロセスやサブエージェントに委任することが許可されている場合は、`codex-review` スキルを使う。禁止されている場合は、自分で同じ差分をレビューする。レビューの実行方法が禁止されていることだけを理由に停止しない。各指摘を実際のコードで確認する。事実関係と修正方法が明確な指摘は修正し、誤りだと確認できた指摘は根拠を示して却下する。ユーザーの判断によって修正内容が変わる指摘だけをユーザーへ提示する。

PRは原則1本にまとめる。レビュー負荷の軽減を理由にPRを分割しない。分割すると各PRの文脈・依存関係・マージ順の確認が必要になり、レビュー負荷が増える。どうしても1本にまとめられず、複数のPRへの分割が不可欠な事情がある場合に限り、分割前にユーザーへ許可を求める。1本にできない具体的な理由、必要なPRの本数、各PRに含める変更、依存関係とマージ順を提示し、明示的な許可を得るまで分割に着手しない。変更行数や変更ファイル数が多いこと、段階的に実装したいことだけでも、分割したり分割の許可を求めたりしない。specや計画に分割が書かれているだけでは許可とみなさない。ユーザーがその分割を明示的に許可済みなら、同じ許可を再度求めない。

分割の許可を得た場合は、stacked PR にする（2本目以降は先行PRのブランチをベースにする）。分割したときの完了条件は全PRの作成とCI通過であり、途中のPRで停止しない。

すべての完了条件を満たした後に、Semantic Commit 形式でのコミット、現在のブランチへのプッシュ、PR の作成、CI の確認を行う。明示的な `$implement` はこれらを含む手順の実行依頼なので、会話上の確認を工程ごとに繰り返さない。実行環境がツールの承認を要求する場合は、その承認機能を使う。承認後は同じターンで作業を続ける。この承認は、破壊的な操作、マージ、デプロイ、別ブランチの上書きを許可するものではない。

進捗を報告するだけでターンを終了しない。安全な代替手段で続行できず、完了にユーザーの新しい判断が本当に必要な場合だけ停止する。CI が完了しない、または失敗する場合は原因を調査し、依頼範囲で修正できるものは修正して再実行する。依頼範囲を変える判断が必要な場合は、原因と未達条件を報告して判断を求める。
