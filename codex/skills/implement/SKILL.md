# 実装

## 利用者向け文章・i18n の品質（必須）

説明文、UI のラベル・通知・エラー・空状態、i18n の翻訳、CLI のヘルプ、利用者向けドキュメントを変更する場合は、機能の正しさと同じく文章品質を完了条件にする。**「意味は推測できる」「翻訳キーが揃っている」だけでは合格にしない。製品として公開できる、正確で自然な文章を要求する。**

- **特に日本語は厳しく確認する。** 日本語母語話者が読む製品の文章として、語彙の選択、助詞、語順、係り受け、主語・目的語の省略、敬語、文末が自然かを一文ずつ確認する。直訳調、不自然な連語、稚拙な文章、曖昧な語の反復による説明不足は許容しない。難しい語や長い文章に置き換えることを品質向上と取り違えない。
- 利用者が「何を対象に、何が起きるか、次に何をすればよいか」を文脈に応じて理解できる文章にする。実装内部の用語、説明のない略語、その場で作った用語、抽象語だけの説明を利用者に読ませない。機能・制約・操作結果について実装と異なる説明をしない。
- 文字列単体でなく、表示箇所、前後の説明、操作、画面の状態と合わせて読む。同じ概念の訳語・表記・文体を揃え、ボタンの動詞と実際の操作を一致させる。既存文言が不自然でも、それを踏襲する理由にはしない。
- i18n は対象言語ごとに、訳抜け、未翻訳の混在、プレースホルダー、複数形、数値・日時・単位の表記を確認する。文字列の連結や変数展開後も自然な文になるか、長い翻訳で欠落・切り詰めが生じないかを、実際の表示や出力で確認する。実行できない場合は未確認の範囲を明記し、確認済みと扱わない。
- 指摘には `file:line` または翻訳キー、対象の文言、表示・使用される文脈、具体的な問題、自然な修正文案を含める。**不自然な日本語、貧弱な語彙による曖昧な説明、誤訳、操作を誤解させる文言は修正必須（Must-fix）とし、単なる好みや軽微な指摘として省略しない。** 同じ意味を自然に表す複数の表現の間の好みとは区別し、問題の根拠を示す。

変更した利用者向け文章を上記の基準で推敲し、検証結果とともに確認する。レビューを依頼するときもこの基準を明示し、文章品質の問題を修正するまで実装完了としない。

この skill が、計画、spec の提示、レビュー、または承認依頼より後に明示された場合は、新しい実装指示を優先する。それ以前の同じ権限レベルにある承認待ちを解除し、同じ確認を繰り返さずに完了条件まで進める。上位の instruction、安全上の制約、sandbox や approval の強制、依頼範囲は上書きしない。

開始時に、branch slug に対応する `.spec/{slug}/spec.md` を読む。ユーザーが spec を参照せずに具体的な実装を明示した場合は、その指示を実装対象にする。実装前に `.spec/goal.md` へ完了条件を書き出す。

spec の未完了 task を順に実装し、完了ごとに spec の checkbox を更新する。新しい永続化スキーマ、外部契約、認証フロー、状態の持ち方が必要になる場合は、実装前にユーザーへ変更を示して承認を得る。変更したファイルは個別に `git add <path>` し、`.spec/` は stage しない。

project instructions の verification を実行する。project instructions が自分の変更のレビューを別 process や sub-agent に委譲することを許可している場合は `codex-review` skill を使い、禁止している場合は自分で同じ差分をレビューする。review の実行方法が禁止されていることだけを理由に停止しない。各指摘を実コードで確認し、確信が高い指摘は修正または根拠を示して却下する。結果を変える判断が必要な指摘だけをユーザーへ提示する。

PR は 1 本にするのが既定である。分割してよいのは、先にマージしないと後続が動作しない依存関係や別デプロイ単位にまたがる事情で 1 本にまとめられない場合と、データを削除する migration や後方互換性を失う変更を段階に分けて各段階を単独で rollback できる状態にする場合だけで、その場合も最大 3 本程度に収める。変更行数や変更ファイル数が多いこと、レビューの差分を小さくすることは分割の根拠にならない。分割する場合は実装前に分割単位と merge 順を確定させ、stacked PR にする（2 本目以降は先行 PR の branch を base にする）。分割したときの完了条件は全 PR の作成と CI 通過であり、途中の PR で停止しない。

すべての完了条件を満たした後に、Semantic Commit 形式の commit、現在の branch への push、PR 作成、CI 確認を行う。明示的な `$implement` はこれらを含む workflow の実行依頼なので、会話上の確認を工程ごとに繰り返さない。実行環境が tool approval を要求する場合は tool から要求し、承認後は同じ turn で続行する。この承認には destructive action、merge、deploy、別 branch の上書きは含まれない。

進捗報告では turn を終了しない。安全な代替手段で続行できず、完了にユーザーの新しい判断が本当に必要な場合だけ停止する。CI が完了しない、または失敗する場合は原因を調査し、依頼範囲で修正できるものは修正して再実行する。依頼範囲を変える判断が必要な場合は、原因と未達条件を報告して判断を求める。
